## 2.1 说辞
    
### 2.2 为什么会有DeepResearcher 去重做这个架构
    

我在高德实习期间，主要负责了内部订单诊断系统的架构重构。

V1.0 版本是一个典型的单轮扁平化工具调用 。它的逻辑是：用户提问 -> 并行调用2-3个工具（查账单、轨迹） -> 汇总给 LLM -> 生成回答。 当前的架构对于在处理简单事情：比如查车费的时候效果很高，但在面对复杂的**问题**时，就会错失很多信息。

> 我就拿一个经典的价格超出预期的例子。有人问 xxxx 订单超出预期价格的原因。这个看似是一句话，但是其实包含着至少三层意思：
> 
> 1. 找出订单开始时候是怎样的，订单实际支付了是多少
>     
> 2. 判断订单是否超出预期
>     
> 3. 再进行下一步调用别的工具去找原因
> 
>原来的版本的话，就只能找到浅层的是不是超出预期，不能进行深度的研究。所以，我意识到当前架构的一个**瓶颈**就是： 【返回的信息不够，没办法推导解决复杂问题】。

---

### 2.2 怎么去解决这个问题
    
#### 2.2.1  SuperAPI 的缺陷
    

当时最直觉的反应是，既然是返回的信息不够，那么做一个Super API 不就行？

为什么不做 Super API（一次性拉取所有数据）？最直观的做法是把所有能查的数据全查回来给大模型。基于以下两点，我否定了这个方案：

1. Lost in the Middle 的问题，或者是上下文压力。虽然有些模型号称上下文窗口 128 K，但是当你塞满 100k 的内容时，模型往往能记住开头和结尾，但容易忽略中间的信息。即使我们能拉取海量数据，一次性灌入大量无关信息（比如无关的轨迹点、正常的历史订单），也 会极大地稀释有效信息。 在长文本下，大模型的**注意力机制****（Attention）** 会分散，导致‘幻觉’——即模型开始根据无关噪音编造理由，而不是根据核心线索推理。
    
2. 工程上的‘数据依赖（Data Dependency）’：还有一个是你返回的全量信息并不一定是全量的，你不先查‘流水’发现有‘重派’，就根本不知道要去查‘前序司机’的违规记录。
    

其实，不使用 Super API，还有一个更底层的 AI 原理考量。我看过 Google DeepMind Denny Zhou 的研究，他提出过一个核心观点：**模型解决问题的复杂度，与它消耗的中间推理的数量成正比。**

- **Super** **API** **模式（单次调用）**： 如果我们在一次 Super API 调用中要求它直接给出结论，本质上是在强迫模型做‘快思考’。模型的‘计算深度’是不够的，它只能做浅层的模式匹配，做不了深度的逻辑推演。
    
- **多轮交互：**本质上是在构建 **慢思考**。 我们把一个大问题，拆解成了多轮的 `Observation -> Thought -> Action`。 每一轮交互产生的 Token，都是模型在**铺垫计算路径** 。
    

**通过拉长推理链路，把一个单次调用无法承载的**思考路径和 **模型的计算能力**，拆解到了时间轴上。

> 循环调用举例
> 
> 首先，我举个具体的场景，比如处理一个经典的‘改派溢价’**客诉。**
> 
> **如果是旧架构，按照静态规则，碰到‘费用疑问’，它只会死板地去调** **`common_agent`** **查账单。 查出来的结果往往是：‘账单计算无误，符合计价规则’。**
> 
> **客服拿到这个结论是崩溃的，因为这解释不了为什么用户觉得贵。真正的根因可能藏在**前序流程里：
> 
> - 比如‘前一个司机恶意拒单，导致系统被迫改派了远处的车，触发了动态调价’。 这就引出了我们架构最核心的约束：**很多下游 Agent 的入参，强依赖于上游 Agent 的发现。** 不查清楚‘前序’，你根本不知道该去查哪一个‘后序’。
>     
> - 也有可能改派，是供应商突然拒绝单进行改派，我们就要查询这么几分钟内进行改派是是否符合规则
>     
> - 也有可能是绕路，然后价格上涨，这时候就要去看是不是恶意绕路，是因为原路线堵车。
>     
> - 也有可能是堵车，导致行驶时间长导致的堵车
>

#### 只用 Researcher 的效果
    

在架构演进的初期，我确实尝试过最轻量级的方案：**单 Agent 循环调用（Single-Agent ReAct Loop）**。我当时构建了一个包含 20 个高难度客诉的 Golden Dataset 进行 A/B Test。

结果非常令人失望：**单 Agent 的解决率（Pass Rate）不足 60%**，相较于旧版提升微乎其微。

仔细研究日志，发现，当任务步骤超过 7-8 步时，单 Agent ‘逻辑崩坏’的概率大大增加——**要么忘记了最初的目标，要么在海量的工具返回结果中迷失了方向。**

但是执行效果我尝试后，发现和原有架构提升并不是很明显，20条数据集里，覆盖率不足 60%。相比 V1 的提升非常边缘化。

多智能体系统之所以有效，主要是因为它们能够帮助智能体消耗足够的令牌来解决问题。

> GPT 的测试
> 
> 在我们的分析中，三个因素解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评估（该评估测试浏览智能体查找难以找到的信息的能力）中 95% 的性能差异。

我们发现，令牌使用量本身就能解释 80% 的差异，工具调用次数和模型选择是另外两个解释因素。这一发现验证了我们的架构，该架构将工作分配给具有独立上下文窗口的智能体，从而增加了并行推理的能力。多智能体架构能够有效地扩展令牌使用量，以应对超出单个智能体能力范围的任务。

多智能体系统的真正的价值不仅在于拆分任务，更在于提供了一种架构来克服单个上下文窗口的限制。

通过在许多智能体之间并行工作，它们可以将海量的 Token 应用于一个问题——这是单个智能体根本无法做到的。

多智能在克服单个上下文窗口限制的同时，子智能体（Subagents）各自拥有独立的上下文窗口，可以同时探索问题的不同方面，

### DeepResearch 的架构
    

我们当时其实是设计了三层的架构，第一层是 Supvisor，这是一层的主要职责就是将当前的问题划分为多个 Topic 然后，并发调用Researcher 去进行针对一个具体的 Topic 的研究。

Researcher 再去调用多个具体的功能 Agent 去进行操作，每次操作完成后，都会进行反思工具执行的结果，如果需要进一步研究，就会继续调用下一个功能Agent 进行执行。【 想，查，拼，回】

这样子每个智能体可以处理的上下文窗口就得到了大幅度的提升。

但是在这里，我想说的是，因为是由三层架构，所以势不可挡的存在幻觉放大的问题，针对这个问题，我们采用了关键参数提取然后透传的思路，让每一层 Agent 进行执行具体的任务的时候，都知道是为了哪一个 订单号进行执行的。

对于长上下文幻觉问题，我们经常会碰到比如说，给了一个长下文，但是大模型直接不看，开始胡编乱造。在这里，我们采用 引用 的思路，来标记每个结论来自哪个智能体。这也是常用的方法。

同时，我们还通过设置明确的防护措施来主动减轻意外的副作用，防止智能体失控。比如限制，Researecher 的并发数量，Supvisor 最大执行次数，Researcher 的最大执行次数。

“DeepResearch 需要执行 5-8 步。虽然每一步准确率很高（比如 95%），但 8 步下来的联合概率就是 0.958≈66%。我们要做的就是通过‘反思机制’不断把中间步骤拉回来。”

  
### 总结
    

所以说我们整个项目主要是围绕着扩展中间推理 Token 来做的

  
## 测评
    
### 测评集的构建
    

我们从过去一年的高能级客诉（High-Level Complaints）中，筛选出 **100 个具有定论的复杂 Case**。样本覆盖了几个核心业务，包括但不限于：绕路行驶、供需失衡溢价、改派导致的费用冲突、司机违规拒单、司机和乘客冲突等。

引入业务侧的判责人员，对每个 Case 进行标注。包含

- 订单号
    
- 问题（Optional）
    
- 问题及当时的历史结论是什么，问题真值（中途下车，计价不准，不认可未拼成的价格，司机绕路，超出预估时长，司机绕路是主因，超出预估时长，司机绕路/中途甩客，出租车计价问题，起步偏航+未及时结束费用+出租车，未送达目的地，优惠金额变化，无效投诉，拼车单前后优惠价格）
    
- 责任方（乘客，平台，无法判断）
    
- 问题对应的回答要点，以及对应要点分数，以此来判断覆盖率，作为评测指标，但是一条对应的总分是 10 分
    
- 必备的通过条件，必须要回答的要点，一票否决的核心
    
- 幻觉率，**关键事实性幻觉率（如捏造金额、虚构违规记录），对于中间推理过程的轻微逻辑瑕疵（良性幻觉）可以容忍**
    

> 为什么我的订单只有 5 公里，却收了我 50 块钱？ 因前序司机违规拒单，导致系统触发改派，改派车辆为专车且处于供需失衡区域，故产生合理溢价。
> 
> 找到是改派（3分），找到前序司机违规（4分），解释清楚溢价规则（3分）。
> 
> 如果 Tool 返回了 null，但 Agent 编造了一个原因（如“因为堵车”），记为幻觉。

  

---

在智能体开发的早期阶段，由于有很多容易改进的地方，任何改动往往都会产生显著影响。一个及时的调整就可能将成功率从 30% 提升到 80%。如此大的影响，只需几个测试用例就能发现问题。

我们首先创建了一组大约 20 个查询，这些查询代表了真实的使用模式。测试这些查询通常能让我们清晰地看到改动的影响。我们经常听到人工智能开发团队因为认为只有包含数百个测试用例的大规模评估才有用而推迟评估。然而，最好立即从少量示例开始进行小规模测试，而不是等到能够构建更全面的评估才开始。

---

传统的评估方法通常假设人工智能每次都遵循相同的步骤：给定输入 X，系统应遵循路径 Y 以产生输出 Z。

但多智能体系统的工作方式并非如此。即使起点相同，智能体也可能采取完全不同的有效路径来实现目标。一个智能体可能搜索了三个Agent，而另一个智能体则可能搜索8个Agent，或者它们可能使用不同的路径来找到相同的答案。

由于我们并不总是知道正确的步骤是什么，因此我们通常不能仅仅检查智能体是否遵循了我们预先设定的“正确”步骤。

相反，我们需要灵活的评估方法，既能判断智能体是否在调用关键 Agent 的同时实现了正确的结果。

---

### 效果
    

**证据链完整性（ECR）**：这是提升最显著的指标。旧架构常因 Context 干扰漏掉关键证据，新架构实现了 **88% 的核心证据覆盖率**（Baseline 仅为 42%）。

- _Reality Check:_ 也就是说，对于“改派溢价”这种题，以前模型只能答出“贵了”，现在能答出“因为 A 导致 B，进而导致 C”。
    

**零数据幻觉**：通过引入“工具回环校验”机制，我们将涉及金额、时间、里程等**硬数据的幻觉率控制在 0.5% 以下**（100 个 Case 中仅 1 个出现非关键数值偏差），消除了业务侧上线的最大顾虑。

Agent 最怕 `null`。当所有工具都查不到数据时，模型极易产生**恐慌性幻觉**（为了回答而编造：“因为您信用分不足”）。

---

用户的投诉有时极其主观，比如‘司机态度不好’，但录音中没有脏话。这种处于‘灰色地带’的判责，Agent 很难和人类专家的主观感受完全对齐。

有些 Case 是底层数据本身就没有记录。比如司机虽然显示到达，但实际停在马路对面，这种物理世界的细微偏差，API 没有返回，Agent 无法凭空推理。

> - **API 数据**：`lbs_agent` 返回确实发生了偏航，比推荐路线多走了 3.5km。

>

> 
>   
> 
> 司机态度极其恶劣，一直瞪我，还故意急刹车吓我！
> 
> `security_agent` 显示急加减速次数为 2 次（正常范围内）。`msg_agent` 显示全程无对话，无辱骂关键词。
> 
> 司机长相比较凶，且心情不好全程黑脸。刹车稍微重了一点，但没违规。乘客属于敏感型人格
> 
> **驳回用户诉求**。甚至可能回复：“经核实，司机驾驶平稳，未发现违规，您的投诉不成立。激怒用户，导致客诉升级（High-Level Escalation）。
> 
> 虽然事实层面司机无责，但服务层面（Service Layer）需要共情。

### 下游Agent
    

#### 核心订单与策略类
    

- **`strategy_agent`** **(策略助手)**
    
    - **核心定位**：专注于订单匹配过程的智能助手，支持精细化的供需分析、插单策略评估、无应答分析。
        
    - **详细能力**：
        
        - **供需情况**：查询订单起始位置网格（6、7级）的供需数据，评估供需平衡。
            
        - **插单策略**：分析主单静默插单的服务商及原因。
            
        - **派单距离问题**：分析派单距离过远的原因及详细数据。
            
        - **派单无应答问题**：分析无应答原因及相关数据。
            
        - **司机匹配问题**：分析司机在应答前后的召回、过滤及最终绑单数据。
            
        - **司机飘点问题**：分析司机轨迹是否存在飘点（位置异常）。
            
        - **拒单规则分析**：查询司机被拒单命中的具体规则。
            
        - **路口单识别**：确认订单是否为路口单，了解绑定司机情况。
            
        - **KM调度轮次分析**：查看每轮召回司机数量。
            
        - **订单PK情况**：查询被其他订单抢占的情况。
            
        - **为什么无应答**：分析无应答具体原因。
            
        - **排队子单情况/信息**：排队首子单加分情况及排队信息。
            
        - **应答时间长问题**：分析等待久、耗时长等原因。
            
        - **派单远**：分析为什么派单远。
            
        - **排队第一无应答**：分析排队首无应答情况。
            
- **`common_agent`** **(综合性智能助手)**
    
    - **核心定位**：处理和分析打车订单信息的综合助手。
        
    - **详细能力**：
        
        - **用户订单历史分析**：查询用户近期下单情况、详情及历史。
            
        - **订单标签信息诊断**：分析风控判责标记、价格变动标记、特殊状态（异地单、远程调度、溢价单）。
            
        - **账单与支付核验**：核验费用详情、优惠券使用、随单购、免密支付记录、退款详情。
            
        - **订单行中修改分析**：分析行中修改目的地失败原因（如逃单风险）。
            
        - **取消订单流程诊断**：查询取消订单原因、取消挽留策略执行情况、取消费规则。
            
        - **发票处理信息**：查询开票申请和处理进展。
            
        - **远程调度信息获取**：提供调度方案与策略分析。
            
        - **适用问题示例**：用户是否发单、有哪些新单、是否使用优惠券、行中修改为何失败、是否命中风控标记、价格是否异常等。
            
- **`time_line_agent`** **(时间线助手)**
    
    - **核心定位**：基于时间维度的订单状态追踪。
        
    - **详细能力**：
        
        - 根据订单号查询订单信息。
            
        - 查询订单状态变更情况。
            
        - 确认订单是否存在改派情况。
            
        - 查询订单时间轴信息、详细情况。
            
- **`ride_agent`** **(车型/运力助手)**
    
    - **核心定位**：解决用户车型选择与实际派单不符的问题。
        
    - **详细能力**：
        
        - 处理用户未选择某车型（如专车、出租车、拼车），但系统仍派发或绑定了该类型的情况。
            
        - 处理用户期望的用车类型与派单结果不一致。
            
        - 处理用户对叫车类型（优享、豪华车等）表示疑惑或不满。
            
        - 接单运力来源信息。
            

#### 轨迹、位置与导航类

- **`lbs_agent`** **(位置与轨迹助手)**
    
    - **核心定位**：针对上下车点争议、接送驾路线争议、轨迹与偏航问题的诊断。
        
    - **详细能力**：
        
        - **上车点/下车点争议**：用户或司机认为系统推荐点不准确、跨路、过远或存在禁限行。
            
        - **接送驾路线争议**：用户或司机对系统推荐路线、实际行驶路线不认可。
            
        - **行车轨迹与偏航问题**：分析是否偏航、系统偏航判定的合理性。
            
        - **里程计算争议**：针对订单里程、计费里程的计算结果不认可。
            

#### 管控、客诉与合规类
    
- **`controller_agent`** **(管控与客诉助手)**
    
    - **核心定位**：用于司机管理、订单管控及客诉问题（最复杂的 Agent 之一）。
        
    - **详细能力**：
        
        - **订单判责**：查询取消判责、处罚处置详情。
            
        - **干预过程**：查询订单干预的具体过程和可乘轨迹特征。
            
        - **司机违规与处置**：查询司机违规记录、违规处置措施。
            
        - **拒单与申诉**：查询司机拒单记录及申诉审核详情。
            
        - **服务质量指标**：分析司机服务分、完单量、客诉率、违规率、活跃度。
            
        - **权益与补贴**：查询司乘相关补贴金额、优惠券情况。
            
        - **录音与静默**：获取车内录音记录、查询车内静默播单情况及原因。
            
        - **轨迹与接送驾**：获取司机乘轨轨迹、接驾和送驾信息。
            
        - **行中干预**：获取行中干预信息（如安全提醒）。
            
        - **注册信息**：获取司机注册信息、完单信息。
            
        - **客诉详情**：获取司机近期客诉总结、乘客投诉、热线记录。
            
        - **具体客诉场景诊断**：针对司机拒绝接驾、车内环境差、服务态度不佳、拒绝配合开空调、频繁打扰、辱骂、不文明用语、私自拼车、绕路、预估价不准/不合理等问题。
            
        - **报备信息**：司机向平台报备记录。
            
        - **特殊费项诊断**：特殊费项分析。
            
- **`customer_agent`** **(售后与评价助手)**
    
    - **核心定位**：处理“售后信息”相关问题。
        
    - **详细能力**：
        
        - **售后与改价关单**：获取订单退款、改价、关单操作详情及原因依据。
            
        - **优惠与打车金**：查询优惠券和打车金的具体发放信息。
            
        - **完单后评价**：获取订单完单后的用户评价反馈及备注信息。
            
        - 适用于全面分析诊断订单质量、售后处置效果与客户满意度场景。
            
- **`enterprise_agent`** **(企业用车助手)**
    
    - **核心定位**：企业用车场景专项支持。
        
    - **详细能力**：
        
        - 获取企业用车下单失败的原因。
            
        - 分析为何需要员工个人支付或者企业支付。
            
        - 查询企业用车为什么命中敏感规则。
            
        - 获取员工所在的企业信息。
            
        - 查询特定员工 ID (`13426017172`) 是哪个员工。
            
        - 查询企业订单的审批流。
            
        - 是否存在有效的制度和申请单。
            

#### 沟通与消息类
    

- **`msg_agent`** **(消息助手)**
    
    - **核心定位**：查询用户与司乘在订单过程中的各类沟通记录。
        
    - **详细能力**：
        
        - **司乘沟通记录**：包括 IM 聊天消息、司乘电话通话等内容。
            
        - **内容下发信息**：查询系统中下发的内容文案、通知文案。
            
        - **短信记录**：查看相关短信发送明细。
            
        - **小蜜对话记录**：用户在订单问题中与小蜜（客服机器人）的沟通内容。
            
        - **IVR外呼信息**：查询订单相关的 IVR（语音外呼）电话记录和详情。
            
        - 了解订单在众验场景下问题的具体下发情况及处理状态。
            

#### 其他/预留类
    

- **`knowledge_agent`** **(领域知识助手)**
    
    - **核心定位**：回答通用业务名词和逻辑。
        
    - **详细能力**：用户询问涉及运力、司机、服务商、订单管理、管控措施、交易策略、支付财务、出租车行业常识等内容。
        
- **`securityRisk_agent`** **(安全风控助手)**
    
    - **状态**：JSON 中 `description` 为空字符串 `""`。
        
    - **推测**：根据命名，应负责处理安全报警、风控拦截等高敏感度事务。
        
- **`market_agent`** **(营销助手)**
    
    - **状态**：JSON 中 `description` 为空字符串 `""`。
        
    - **推测**：根据命名，应负责营销活动、市场推广相关的逻辑。
        

  

## 扩展问题
    
      对于客诉定责这种业务流程非常明确的场景，我们会用传统工程的思路来驯服 LLM。
    
      实现方式 ：将整个诊断流程抽象成一个**有限状态机（FSM）**。例如：
    
    - 状态 1：`订单信息获取中` **只能**调用 `time_line_agent`。
        
    - 状态 2：`异常点识别` 只有在识别到“取消/改派/溢价”等标签后，才允许进入下一个状态。
        
    
      **作用：** 限制模型在特定阶段的决策空间。例如，只有当订单被识别为“企业订单”时，`enterprise_agent` 才会被激活为可选工具。如果当前订单是普通订单，即使模型想调用 `enterprise_agent`，状态机也会在推理之前将其剪枝，从而避免路径偏差。
