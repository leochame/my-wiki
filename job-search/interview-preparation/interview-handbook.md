# 1. DeepResearch

标称参数与实际可用性之间的严重割裂

## 1.1 说辞

### 1.1.1 回答顺序：先结论，后故事

如果面试官觉得我“像讲故事”，通常不是内容有问题，而是**答案出来得太晚**。所以在这份项目表达里，我应该统一采用一个更像面试回答的顺序：

1. **先一句话结论**：我做了什么，解决了什么问题。
2. **再讲背景和判断**：为什么原方案不够，核心瓶颈是什么。
3. **再讲关键动作**：我具体怎么设计、怎么推进、怎么验证。
4. **最后讲结果和价值**：指标怎么变好，这说明了什么。

如果要套到 DeepResearch 这个项目里，开头可以先这样说：

> 先说结论，这个项目我主要做的是把原来的单轮工具调用架构，升级成一个能沿证据链持续调查的 DeepResearch 多智能体系统。  
> 它解决的核心问题不是“回答更流畅”，而是让系统真正能把复杂客诉查明白。  
> 原来的瓶颈是信息粒度不够，单次调用只能回答表面现象，撑不起连续推导。  
> 所以我后面主要做了架构重构、推理链路约束和评测体系搭建，最终把复杂 Case 的核心证据覆盖率从 42% 提升到了 88%。

一个提醒是：**不要从背景开始讲，要从答案开始讲。**

面试里的“故事感”可以保留，但它应该放在结论后面，作为支撑，而不是把面试官带着慢慢走到结论。

### 1.2 为什么会有DeepResearcher 去重做这个架构
    
这个项目最核心的一点，是我们发现“复杂客诉”其实不是一个问答问题，而更像一个多轮调查问题。

V1.0 是一个典型的单轮扁平化工具调用架构，它的路径很直接：用户提问 -> 并行调用 2-3 个工具（查账单、查轨迹） -> 把结果交给 LLM -> 生成回答。

这个架构在回答简单问题时很高效，比如“这单车费怎么算的”；但一旦进入复杂客诉，它就会暴露出一个很明显的问题：它像一个只能“看一眼现场”的新人客服，能描述表面现象，却很难顺着线索继续往下挖。

换句话说，V1 能回答“发生了什么”，但很难回答“为什么会这样”。

> 我拿一个最典型的“价格超出预期”来举例。用户表面上只问了一句话，但这背后其实至少有三层判断：
> 
> 1. 先还原订单最开始的预估价格，以及最后实际支付了多少
>     
> 2. 再判断它到底是不是“真的超预期”，还是用户主观觉得贵
>     
> 3. 如果确实超预期，还要继续顺着证据链往下找根因
> 
> 原来的版本，通常只能停在第二层，最多回答一句“是超预期 / 不是超预期”。但真正困难的部分恰恰在第三层，也就是“为什么”。所以我当时很快意识到，当前架构的真正瓶颈不是模型不会说，而是**返回的信息粒度不够，无法支撑复杂问题的连续推导**。

---

### 1.3 怎么去解决这个问题
    
#### 1.3.1  SuperAPI 的缺陷
    

我的修改思路一开始也想过做一个 Super API，把所有数据一次性拉全，但后来否掉了。因为这样会带来两个问题：第一，长上下文里噪音太多，模型容易 lost in the middle；第二，很多数据依赖是链式触发的，不是你一开始就知道该查什么，而是查到一步才知道下一步去哪查。所以我最后把方案更新成 DeepResearch 架构，也就是把“大问题一次答完”改成“沿着证据链一步步查明白”。 

所以我们后来采用的思路，不是一次性“喂更多数据”，而是让模型沿着时间轴一层层往下查，把单次调用承载不了的思考深度，拆解到多轮研究过程中。


> 循环调用举例
> 
> 我举个很典型的场景，比如处理“改派溢价”客诉。
> 
> 如果是旧架构，系统看到“费用疑问”，通常只会机械地调用 **`common_agent`** 去查账单。最后拿回来的结论往往是：“账单计算无误，符合计价规则。”
> 
> 这个回答对系统来说没错，但对客服和用户几乎没帮助，因为它回答的是“算没算错”，而不是“为什么你会觉得贵”。真正的根因，常常藏在前面的业务链路里：
> 
> - 比如前一个司机恶意拒单，系统被迫改派到更远的车，最终触发动态调价。这时你不先查清楚“前序改派”，就根本不知道后面要去看司机违规记录，还是去看调价策略。
>     
> - 也有可能是供应商突然拒单引发改派，这时重点就变成“这几分钟内的改派是否符合规则”。
>     
> - 也有可能是绕路导致价格上涨，这时又要去区分，到底是恶意绕路，还是原路线堵车后的合理变更。
>     
> - 还有可能本质上只是严重拥堵，价格上涨来自时长增加，而不是路线异常。
>

#### 1.3.2 只用 Researcher 的效果
    

在架构演进初期，我也尝试过一个更轻量的方案：单 Agent 循环调用（Single-Agent ReAct Loop）。我当时构建了一个包含 20 个高难度客诉的 Golden Dataset 做 A/B Test。

结果并不理想，单 Agent 的解决率（Pass Rate）不足 60%。也就是说，它看起来已经会“循环思考”了，但真正遇到长链路问题，还是撑不住。

我后来仔细翻日志，发现一个很典型的现象：当任务步骤超过 7-8 步时，单 Agent 特别容易“逻辑崩坏”。

它的问题不是某一步不会做，而是链路一长就开始失稳: 要么忘了最初要证明什么，要么被海量工具返回结果带偏，最后越查越远。

从结果上看，它和 V1 相比提升非常有限，在这 20 条数据集里，关键证据覆盖率仍然不足 60%。

这也是我后来转向多智能体架构的关键原因。多智能体真正有效，不只是因为“分工更清晰”，更因为它能给复杂问题提供足够的推理预算。

你可以把它理解成，单 Agent 像一个人边查案边记笔记，查到后面脑子很容易乱；多智能体更像一个小组协作，每个人盯一条线，最后再统一汇总。

> GPT 的测试
> 
> 在我们的分析中，三个因素解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评估（该评估测试浏览智能体查找难以找到的信息的能力）中 95% 的性能差异。
> 
> 我们发现，令牌使用量本身就能解释 80% 的差异，工具调用次数和模型选择是另外两个解释因素。这一点和我们的实践非常一致：复杂问题不是一句话想明白的，而是要给模型足够的“思考空间”和“试错回合”。
> 
> 所以多智能体系统的真正价值，不只是拆分任务，而是提供了一种方式去克服单个上下文窗口和单条推理链的限制。
> 
> 通过让多个智能体并行探索不同方向，我们实际上是在把更多 Token、更长推理链、更强的上下文隔离能力，一起压到同一个复杂问题上。这是单个智能体很难做到的。
> 
> 每个子智能体都有独立的上下文窗口，它们可以同时沿着不同假设往前探索，再把结果回收汇总。

### 1.4 DeepResearch 的架构
    

我们最后设计的是一个三层架构。面试里如果我要把它讲得更直观，我一般会把它描述成一个“总指挥 + 专题调查员 + 专业工具人”的协作体系。

第一层是 `Supervisor`，它不亲自下场查细节，也不会一开始就猜原因。它更像是在先分工：把一个复杂问题横着拆成几个并行 Topic，让不同的 `Researcher` 从不同角度同时去看，而不是上来就先假设“是不是改派导致”或者“是不是绕路导致”。

比如用户问：“为什么我这单才 5 公里却收了 50 块？”  
`Supervisor` 不会先猜结论，而是会先把问题横着铺开，拆成几个 Topic：

- `Billing Topic`：只看价格构成、预估价、实付价、优惠变化、附加费变化
- `Dispatch Topic`：只看接单、取消、改派、司机切换、供应商切换
- `Trajectory Topic`：只看路线、里程、时长、偏航、异常停留
- `Interaction Topic`：只看司乘沟通、客服记录、是否有用户主动要求变更
- `Policy Topic`：只看计价规则、调价策略、当时命中的业务规则

这样做的好处是，`Supervisor` 只负责把搜索空间铺开，不负责提前下结论。最后真正的原因，不是上层拍脑袋猜出来的，而是下面各个 `Researcher` 顺着自己的线索查出来的。

第二层是 `Researcher`。它更像专题调查员，会围绕一个 Topic 持续工作。这里有一个很关键的点：`Researcher` 并不是拿到 Topic 就立刻按某个固定原因去查，而是会先调用 `timeline agent`，把自己这个视角下的重要事件沿时间轴串起来，先还原现场，再决定下一步要查什么。拿到时间线之后，它才会继续调用具体功能 Agent 获取证据，拿到结果后做一次反思，如果信息还不够，就继续决定下一步查什么。这个过程其实就是一个不断循环的【想，查，拼，回】。

这样做之后，每个智能体只需要盯住自己那一小块问题，局部上下文就会干净很多，整体可处理的信息规模也就自然拉大了。

所以它的本质不是把一个 Agent 变得无限强，而是把复杂问题拆成多个“局部可解”的小战场。

当然，三层架构也不是没有代价。层级一多，就会天然出现“幻觉放大”的风险: 上一层如果把问题理解偏了，下一层可能会沿着错误方向越走越远。

所以我们专门做了关键参数提取和透传，让每一层 Agent 在执行时都明确知道自己正在处理哪个订单号、哪个用户问题、当前要验证的核心假设是什么，避免链路传着传着就“串单”或者“跑题”。

对于长上下文下的幻觉问题，我们还引入了“引用”机制，要求关键结论都能标记来源，说明它来自哪个智能体、哪次工具调用。这样最后输出给人的不是一句悬空判断，而是一条能追溯的证据链。

同时，我们也加了很多工程上的护栏，防止智能体失控，比如限制 `Researcher` 的并发数量、限制 `Supervisor` 的最大执行次数、限制单个 `Researcher` 的最大循环次数。

因为 DeepResearch 这种架构最怕的，不是“不会查”，而是“查疯了”或者“查偏了”。

“DeepResearch 往往需要执行 5-8 步。虽然每一步看起来都很准，比如有 95%，但 8 步串起来的联合成功率其实只有 0.95^8，差不多 66%。所以这个架构的关键，不只是让它往前走，而是通过反思和校验机制，尽量把每一步都往正确方向拉回来。”

  
### 1.5 总结
    

所以总结一句，这个项目本质上不是在“堆更多工具”，而是在围绕一件事做架构设计：**怎么把中间推理 Token 有效地扩展开，让模型真的有能力把复杂问题一步步查明白。**

如果用一句更适合面试收尾的话来说，就是：**我们不是让模型更会回答了，而是让它更像一个会做调查的系统。**

  
## 2. 测评
    
### 2.1 测评集的构建
    
在这个项目里，我们重点就看两件事：
    
- **结论对不对**：最后判的是谁的责任、退不退款，这些结果有没有和业务的“真值”对上。
- **证据找全没**：关键证据有没有被覆盖到，比如轨迹、改派记录、风控标记、语音记录这些。
    
这里有一条很硬的规则：有些「必备要点」如果没说到，直接判不过关。比如这个 Case 里，如果你没找到“前序司机违规改派”这个关键点，那后面再怎么解释都没用。
    
我们是从过去一年的高能级客诉（High-Level Complaints）里，挑了 **100 个结论比较清晰的复杂 Case** 出来做测评集。里面覆盖了好几个核心业务场景，比如绕路行驶、供需失衡导致的溢价、改派引起的费用纠纷、司机违规拒单、司机和乘客的冲突等等。
    
对每个 Case，我们把 Agent 的目标拆成了两层：
    
1. **Outcome 层面**：看 Agent 最终给出的判责 / 处理结论，是不是和业务同学认定的真值一致。
2. **Process 层面**：看它在推理的过程中，有没有把关键证据链都走一遍、说清楚。
    
这套评估我们不是自己拍脑袋定的，而是拉上了业务侧真正做判责的同学，一起把每个 Case 结构化标注了一遍，大概包括：
    
- 订单号
- 问题描述（可选）
- 问题和当时的历史结论，以及对应的“真值”（比如：中途下车、计价不准、不认可未拼成价格、司机绕路、超出预估时长、司机绕路是主因、出租车计价问题、起步偏航 + 未及时结束费用 + 出租车、未送达目的地、优惠金额变化、无效投诉、拼车单前后优惠价格等）
- 责任方（乘客 / 平台 / 司机/无法判断）
- 回答里需要覆盖的关键要点，以及每个要点的分值，总分是 10 分，用来评估覆盖率
- 必须要提到的一票否决型要点（ 漏掉就算不过关,关键因果点没抓到 ）
- 幻觉情况，重点关注**关键事实性的幻觉**（比如捏造金额、虚构违规记录）；对中间推理里一些不影响结论的小瑕疵，我们是允许有一点“良性幻觉”的。
    
> 比如有个典型问题是：  
> “为什么我的订单只有 5 公里，却收了我 50 块钱？”  
> 真实原因是：前序司机违规拒单 → 触发改派 → 改派到专车 + 供需失衡 → 溢价。
> 在这个 Case 里，像“找到是改派”（3 分）、“找到前序司机违规”（4 分）、“把溢价规则讲清楚”（3 分），加起来才算 10 分。  
> 如果工具查出来是 null，但 Agent 硬编一个理由，比如“因为堵车所以贵”，这种我们就直接记成幻觉。
> 如果回答里完全没提“前序司机违规/改派”这一条，就会被直接一票否决，哪怕你后面把溢价规则解释得再漂亮都没用。

> 触发一票否决必须满足以下核心缺陷之一：
> - 判责归因错误 (Fatal Outcome Error)： 最终的结论与“真值”完全相悖
> 	- 本该是乘客违规操作，Agent 却判定司机有责并建议扣款。
> 	- 乘客主动要求绕路（沟通记录有佐证），Agent 却将责任判定为“司机恶意绕路”。
> 
> - 关键证据链断裂 (Critical Evidence Missing)： 得出了正确的结论，但是支撑该结论的**唯一核心证据**缺失。
> 	- 判断“前序司机违规导致溢价”，但完全没有调用或体现 `controller_agent` 中前序司机的违规记录。这种属于典型的“瞎猫碰上死耗子”或“严重事实幻觉”，在复杂系统中不可信任，同样一票否决。
>
>质量评估：打分与扣分制（The Deductive Scoring System）。更精细地反映不同 Agent 运行路径的质量。
>- 缺乏二级证据支撑
>	- 已经找到了“前序司机违规改派”的核心证据，但缺失了 `strategy_agent` 对具体策略规则（“供需失衡/动态调价具体规则/倍数”）的拉取，导致无法向用户精确解释为什么贵了这么多。扣 -3 分。
>	- 指出司机“服务态度恶劣/有沟通冲突”，但未能提取录音或消息中的具体异常沟通时间点或高风险关键词。
>	- 核心轨迹偏航已查清。但缺失了对 `time_line_agent` 中“偏航时间点是否有严重拥堵/封路日志”的排查，或者没调取 `msg_agent` 查看司乘沟通记录（看是否有口头协商）
>- 但缺乏精确的数值对比，导致客服依然需要自己去算账。
>	- 查出绕路，但没有写明“实际比推荐路线多走了 X.X 公里”。
>	- 查出优惠券变化，但没有列出“原优惠 X 元，现优惠 Y 元，实付差额 Z 元”

---

在智能体开发的早期阶段，由于有很多容易改进的地方，任何改动往往都会产生显著影响。一个及时的调整就可能将成功率从 30% 提升到 80%。如此大的影响，只需几个测试用例就能发现问题。

一句话总结 evals 的价值：**在代理生命周期的任何阶段，evals 都很有用**——早期它会逼着产品/业务把“成功到底长什么样”先说清楚；后期它能把质量标准钉住，防止改着改着就走样。

我们首先创建了一组大约 20 个查询，这些查询代表了真实的使用模式。测试这些查询通常能让我们清晰地看到改动的影响。我们经常听到人工智能开发团队因为认为只有包含数百个测试用例的大规模评估才有用而推迟评估。然而，最好立即从少量示例开始进行小规模测试，而不是等到能够构建更全面的评估才开始。

---

传统的评估方法通常假设人工智能每次都遵循相同的步骤：给定输入 X，系统应遵循路径 Y 以产生输出 Z。

但多智能体系统的工作方式并非如此。即使起点相同，智能体也可能采取完全不同的有效路径来实现目标。一个智能体可能搜索了三个Agent，而另一个智能体则可能搜索8个Agent，或者它们可能使用不同的路径来找到相同的答案。

由于我们并不总是知道正确的步骤是什么，因此我们通常不能仅仅检查智能体是否遵循了我们预先设定的“正确”步骤。

相反，我们需要灵活的评估方法，既能判断智能体是否在调用关键 Agent 的同时实现了正确的结果。

---

### 2.2 效果
    

**证据链完整性（ECR）**：这是提升最显著的指标。旧架构常因 Context 干扰漏掉关键证据，新架构实现了 **88% 的核心证据覆盖率**（Baseline 仅为 42%）。

- _Reality Check:_ 也就是说，对于“改派溢价”这种题，以前模型只能答出“贵了”，现在能答出“因为 A 导致 B，进而导致 C”。
    

**零数据幻觉**：通过引入“工具回环校验”机制，我们将涉及金额、时间、里程等**硬数据的幻觉率控制在 0.5% 以下**（100 个 Case 中仅 1 个出现非关键数值偏差），消除了业务侧上线的最大顾虑。

Agent 最怕 `null`。当所有工具都查不到数据时，模型极易产生**恐慌性幻觉**（为了回答而编造：“因为您信用分不足”）。

## 3. 凸显思考

### 3.1上线后的收益怎么讲

线上完整解决率我没有闭环数据，所以不硬报；但离线是有量化的，早期单 Agent Pass Rate 不足 60%，升级后在 100 个复杂 Case 上，核心证据覆盖率从 42% 提升到 88%，硬数据幻觉率降到 0.5% 以下。这说明复杂问题的解决质量是明显提升了。

### 3.1 下游Agent
    

#### 3.1.1 核心订单与策略类
    

- **`strategy_agent`** **(策略助手)**
    
    - **核心定位**：专注于订单匹配过程的智能助手，支持精细化的供需分析、插单策略评估、无应答分析。
        
    - **详细能力**：
        
        - **供需情况**：查询订单起始位置网格（6、7级）的供需数据，评估供需平衡。
            
        - **插单策略**：分析主单静默插单的服务商及原因。
            
        - **派单距离问题**：分析派单距离过远的原因及详细数据。
            
        - **派单无应答问题**：分析无应答原因及相关数据。
            
        - **司机匹配问题**：分析司机在应答前后的召回、过滤及最终绑单数据。
            
        - **司机飘点问题**：分析司机轨迹是否存在飘点（位置异常）。
            
        - **拒单规则分析**：查询司机被拒单命中的具体规则。
            
        - **路口单识别**：确认订单是否为路口单，了解绑定司机情况。
            
        - **KM调度轮次分析**：查看每轮召回司机数量。
            
        - **订单PK情况**：查询被其他订单抢占的情况。
            
        - **为什么无应答**：分析无应答具体原因。
            
        - **排队子单情况/信息**：排队首子单加分情况及排队信息。
            
        - **应答时间长问题**：分析等待久、耗时长等原因。
            
        - **派单远**：分析为什么派单远。
            
        - **排队第一无应答**：分析排队首无应答情况。
            
- **`common_agent`** **(综合性智能助手)**
    
    - **核心定位**：处理和分析打车订单信息的综合助手。
        
    - **详细能力**：
        
        - **用户订单历史分析**：查询用户近期下单情况、详情及历史。
            
        - **订单标签信息诊断**：分析风控判责标记、价格变动标记、特殊状态（异地单、远程调度、溢价单）。
            
        - **账单与支付核验**：核验费用详情、优惠券使用、随单购、免密支付记录、退款详情。
            
        - **订单行中修改分析**：分析行中修改目的地失败原因（如逃单风险）。
            
        - **取消订单流程诊断**：查询取消订单原因、取消挽留策略执行情况、取消费规则。
            
        - **发票处理信息**：查询开票申请和处理进展。
            
        - **远程调度信息获取**：提供调度方案与策略分析。
            
        - **适用问题示例**：用户是否发单、有哪些新单、是否使用优惠券、行中修改为何失败、是否命中风控标记、价格是否异常等。
            
- **`time_line_agent`** **(时间线助手)**
    
    - **核心定位**：基于时间维度的订单状态追踪。
        
    - **详细能力**：
        
        - 根据订单号查询订单信息。
            
        - 查询订单状态变更情况。
            
        - 确认订单是否存在改派情况。
            
        - 查询订单时间轴信息、详细情况。
            
- **`ride_agent`** **(车型/运力助手)**
    
    - **核心定位**：解决用户车型选择与实际派单不符的问题。
        
    - **详细能力**：
        
        - 处理用户未选择某车型（如专车、出租车、拼车），但系统仍派发或绑定了该类型的情况。
            
        - 处理用户期望的用车类型与派单结果不一致。
            
        - 处理用户对叫车类型（优享、豪华车等）表示疑惑或不满。
            
        - 接单运力来源信息。

## 4. 扩展问题
    
      对于客诉定责这种业务流程非常明确的场景，我们会用传统工程的思路来驯服 LLM。
    
      实现方式 ：将整个诊断流程抽象成一个**有限状态机（FSM）**。例如：
    
    - 状态 1：`订单信息获取中` **只能**调用 `time_line_agent`。
        
    - 状态 2：`异常点识别` 只有在识别到“取消/改派/溢价”等标签后，才允许进入下一个状态。
        
    
      **作用：** 限制模型在特定阶段的决策空间。例如，只有当订单被识别为“企业订单”时，`enterprise_agent` 才会被激活为可选工具。如果当前订单是普通订单，即使模型想调用 `enterprise_agent`，状态机也会在推理之前将其剪枝，从而避免路径偏差。
