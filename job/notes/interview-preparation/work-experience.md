## 1. DeepResearch

### 1.1 说辞

#### 1.1.1 回答顺序

总的来讲，我们这个是对内的平台，主要去处理用户的投诉和反馈。我做的工作就是把原来的单轮多工具调用架构，升级成一个多轮工具调用的多智能体架构。

我们做这个事情的目的，就是为了让平台不再仅仅限于一问一答的任务，而能够处理更加复杂的客诉问题。

最终架构其实是三层 agent 架构：第一层领导者，第二层研究员，第三层专家 agent 。

---

**a. 背景 - 瓶颈**

原来的单轮工具调用架构的路径就是：用户提问 -> 并行调用 2-3 个工具（查账单、查轨迹） ->  把结果交给 LLM -> 生成回答。这种架构只能回答是什么类型的任务，很难顺着线索继续往下挖。

我们可以认识到这里的瓶颈有两个：
1. 一个是信息不够多，因为每次只调两三个功能 agent，信息不足以支撑回答整个问题。
2. 还有一个是任务是研究类型的，会动态调查，存在数据依赖，必须先从某个 agent 获取到信息，然后才能从另一个中获取到信息。

> **举例说明**
>
> 我拿一个最典型的"价格超出预期"来举例。用户表面上只问了一句话，但这背后其实至少有三层判断：
> 1. 先还原订单最开始的预估价格，以及最后实际支付了多少
> 2. 再判断它到底是不是"真的超预期"，还是用户主观觉得贵
> 3. 如果确实超预期，还要继续顺着证据链往下找根因
> 原来的版本，通常只能停在第二层，最多回答一句"是超预期 / 不是超预期"。

----

**b. 如何解决的**

所以说，我们的最佳实现路径是一个增加一个研究员的角色，可以执行多轮反复调用的功能，每次做的事情是，先思考要调用哪些 agent ，真正去调用这个 agent，然后根据返回的信息，确定下一轮调用，如此反复多轮去解决了这个问题。

但是在这里，我们是还增加一个领导者的角色，最终会落地去呈现的是一个 总指挥 + 专题调查员 + 工具 的这样的协作体系。
1. 第一层是 `Supervisor`，它不亲自下场查细节，也不会一开始就猜原因。它更像是在先分工：把一个复杂问题横着拆成几个并行 Topic，而不是上来就先假设什么原因导致的。 它不查具体数据，而是先把一个大问题拆成几条线，比如账单、轨迹、策略、司乘沟通这几条。
2. 第二层是 `Researcher`。它更像专题调查员，会围绕一条线持续工作。它调用具体功能 Agent 获取证据，拿到结果，如果信息还不够，就继续决定下一步查什么。这个过程其实就是一个不断循环的【想，查，拼，回】。 
3. 最后真正的原因是汇总下面各个 `Researcher` 顺着自己的线索查出来的。

>比如用户问："为什么我这单才 5 公里却收了 50 块？" `Supervisor` 不会先猜结论，而是会先把问题横着铺开，拆成几个 Topic：
>
>- `Billing Topic`：只看价格构成、预估价、实付价、优惠变化、附加费变化
>- `Dispatch Topic`：只看接单、取消、改派、司机切换、供应商切换
>- `Trajectory Topic`：只看路线、里程、时长、偏航、异常停留
>- `Interaction Topic`：只看司乘沟通、客服记录、是否有用户主动要求变更
>- `Policy Topic`：只看计价规则、调价策略、当时命中的业务规则

**上下文腐烂阈值**

上下文窗口的最大限制，其实模型供应商给的限制，就是在考虑成本等多重因素之下。但是模型的实际可以处理的有效上下文更小，过多就会出现上下文腐烂的问题。

我们会首先去判断上下文腐烂的阈值在哪里，我们经过多次尝试后，发现 7～8 轮后模型就倾向于停结束任务，并且再次之后，人为强行增加上下文或者强制调用，之后的压缩效果等等都会大打折扣，这个 阈值是 80k ～ 100 k 之间，在当时 Qwen3 的测试中。

所以我们的解决方法就是增加一层 Supvisor Agent，来增加上下文总窗口。这个其实就是变成了多智能体的架构。


**幻觉处理**

我想这里想额外补充一点，就是我们在明知多智能体会放大幻觉，为什么我们还采用多智能体的架构？

我其实是比较坚信 DeepMind 的一个结论，“中间推理 Token”生成的越多，模型的计算能力就会被拓展的越大，从而能够解决更复杂的问题。

但是由于单智能体的上下文窗口是有限的。我们在做的事扩展上下文窗口，从而拉长一个思考链路，生成尽可能多的中间推理 Token 在一个任务上。


**幻觉放大的问题**

当然，三层架构带来的代价就是"幻觉放大"的风险，上一层如果缺失了关键参数或者理解偏了问题，下一层可能会沿着错误方向越走越远。 所以我们专门做了关键参数提取和透传，让每一层 Agent 在执行时都明确知道自己正在处理哪个订单号、哪个用户问题、当前的 topic 是什么。

在查询过程中为了防止模型查偏的问题，我们增加了反思和校验机制，是一个 think_tool，尽量把每一步都往正确方向拉回来。 

> 通过工具返回结果形成隐式反馈。现代大模型（特别是经过 Function Calling 深度优化的基座模型）在训练时，针对 `<|function_call|>` 和 `<|function_result|>`之间的 Token，形成了一种特殊的注意力模式。模型在预测最终回复时，会倾向于将注意力高度聚焦在 `function_result` 返回的结论部分。


**压缩阶段**

>各家有各家的不同，Manus 那块让主 Agent 先定义好输出 Schema，在子 Agent 这一端，它们拥有一个名为 `submit_result`（提交结果）的特殊工具，确保子 Agent 提交回主 Agent 的内容完全符合主 Agent 预先定义的 Schema。你可以把这想象成一种 MapReduce 操作：它会生成类似于电子表格的结果，而这个表格的每一项都严格受限于预设的 Schema。

然后我这边其实是是采用了引证和类 scheme，让模型按照格式输出，Evidence (事实证据)，Reasoning (推导逻辑)，Conclusion (分项结论，也就是每个 Topic 对应 research 给出的结论)。

同时，对于长上下文下的幻觉问题，我们还引入了"引用"机制，要求关键结论都能标记来源，说明它来自哪个智能体、哪次工具调用。可以追溯的同时，保证了在长下文的情况下可以减少模型的幻觉问题。


**Harness Engineer**

我们也加了很多工程上的护栏，防止智能体失控，比如限制 `Researcher` 的并发数量、限制 `Supervisor` 的最大执行次数、限制单个 `Rsearcher` 的最大循环次数。

如果模型返回为空，我们设置任务失败等等明显的提示词。Agent 最怕 `null`。当所有工具都查不到数据时，模型极易产生**恐慌性幻觉**。

#### 1.1.2 总结

这个项目本质上不是在"堆更多工具"，而是在围绕一件事做架构设计：**怎么把中间推理 Token 有效地扩展开，让模型真的有能力把复杂问题一步步查明白。**

多智能体为什么有效：

1. 每个子 Agent 只盯自己的 Topic，局部上下文干净，不被其他 Topic 的噪音干扰
2.  工具调用的次数，Token 消耗的数量。

多智能体架构能够有效地扩展令牌使用量，以应对超出单个智能体能力范围的任务。

通过拉长推理链路，把一个单次调用无法承载的思考路径和 模型的计算能力，拆解到了时间轴上

通过结构化输出传递摘要，完整数据存外部存储（上下文卸载），需要时再读

仔细研究日志，发现，当任务步骤超过 7-8 步时，单 Agent ‘逻辑崩坏’的概率大大增加——要么忘记了最初的目标，要么在海量的工具返回结果中迷失了方向。

#### 1.1.2.1 冷启动阶段的工程经验

这类 Agent 项目最容易被低估的，不是模型本身，而是冷启动时的工程顺序。我的理解是：

1. **先跑通链路，再谈优化**：冷启动阶段先用能力最强的模型把端到端链路打通，先验证“能不能做成”，再去考虑快模型替换、提示词压缩或者后训练。
2. **评测大于一切**：只要链路跑通，第一件事不是继续堆功能，而是把评测集、输入输出、关键中间态全部记录下来。没有评测，后面的优化就没有锚点。
3. **日志**：模型输入、输出、工具调用、耗时、报错、命中路径都要串起来，并且通过异步方式落库，避免日志写入拖慢主链路。
4. **上下文要可恢复**：短期上下文可以放在 Redis 里，既方便恢复，也方便在多轮调用里做状态续接。对 Agent 来说，能恢复上下文比“每次都重新理解”更重要。
5. **参数提取要并发化**：像目的地、出发地、订单号这类下游链路依赖的槽位，不应该串行等待。更合理的做法是把参数提取拆出去，用线程池并发访问，减少整体等待时间。

更像工程师的说法，不是“我在调模型”，而是：

> 我先用最强模型把业务链路跑通，再用评测和日志把每一步钉住，最后再把链路压缩到更便宜、更快的模型上。这个顺序本质上是在先保证正确性，再追求成本和性能。

补一句更像资深工程师的表达是：

> 冷启动阶段最重要的不是模型成本，而是把系统做成“可观测、可恢复、可迭代”的状态。只要链路一旦跑通，后面所有优化都应该建立在评测、日志和上下文恢复这些基础设施之上。

#### 1.1.4 测评

##### 1.1.4.1 测评的流程

在智能体开发的早期阶段，由于有很多容易改进的地方，任何改动往往都会产生显著影响。一个及时的调整就可能将成功率从 30% 提升到 80%。如此大的影响，只需几个测试用例就能发现问题。

一句话总结 evals 的价值：**在代理生命周期的任何阶段，evals 都很有用**——早期它会逼着产品/业务把“成功到底长什么样”先说清楚；后期它能把质量标准钉住，防止改着改着就走样。

我们首先创建了一组大约 20 个查询，这些查询代表了真实的使用模式。测试这些查询通常能让我们清晰地看到改动的影响。我们经常听到人工智能开发团队因为认为只有包含数百个测试用例的大规模评估才有用而推迟评估。然而，最好立即从少量示例开始进行小规模测试，而不是等到能够构建更全面的评估才开始。

##### 1.1.4.2 测评集的构建

在这个项目里，我们重点就看两件事：

**Outcome 层面**：看 Agent 最终给出的判责 / 处理结论，是不是和业务同学认定的真值一致。
**Process 层面**：看它在推理的过程中，有没有把关键证据链都走一遍、说清楚。关键证据有没有被覆盖到，比如轨迹、改派记录、风控标记、语音记录这些。

我们是从过去一年的高能级客诉（High-Level Complaints）里，挑了 **100 个结论比较清晰的复杂 Case** 出来做测评集。里面覆盖了好几个核心业务场景，比如绕路行驶、供需失衡导致的溢价、改派引起的费用纠纷、司机违规拒单、司机和乘客的冲突等等。

- 订单号
- 问题描述（可选）
- 问题和当时的历史结论，以及对应的"真值"
- 责任方（乘客 / 平台 / 司机/无法判断）
- 回答里需要覆盖的关键要点，以及每个要点的分值，总分是 10 分
- 必须要提到的一票否决型关键要点，如果你没找到“前序司机违规改派”这个关键点，那后面再怎么解释都没用。
- 幻觉情况，重点关注**关键事实性的幻觉**


> 比如有个典型问题是：
> "为什么我的订单只有 5 公里，却收了我 50 块钱？"
> 真实原因是：前序司机违规拒单 → 触发改派 → 改派到专车 + 供需失衡 → 溢价。
> 在这个 Case 里，像"找到是改派"（3 分）、"找到前序司机违规"（4 分）、"把溢价规则讲清楚"（3 分），加起来才算 10 分。
> 如果工具查出来是 null，但 Agent 硬编一个理由，比如"因为堵车所以贵"，这种我们就直接记成幻觉。
> 如果回答里完全没提"前序司机违规/改派"这一条，就会被直接一票否决。

> 触发一票否决必须满足以下核心缺陷之一：
> - 判责归因错误 (Fatal Outcome Error)：最终的结论与"真值"完全相悖
> - 关键证据链断裂 (Critical Evidence Missing)：得出了正确的结论，但是支撑该结论的**唯一核心证据**缺失

一句话总结 evals 的价值：**在代理生命周期的任何阶段，evals 都很有用**——早期它会逼着产品/业务把"成功到底长什么样"先说清楚；后期它能把质量标准钉住，防止改着改着就走样。

---

##### 1.1.4.3 效果

旧架构常因 Context 干扰漏掉关键证据，新架构实现了 80%多 的核心证据覆盖率（Baseline 仅为 42%）。

通过引入"工具回环校验"机制，我们将涉及金额、时间、里程等硬数据的幻觉率控制在 0.5% 以下，消除了业务侧上线的最大顾虑。

上线后，调用次数统计超日均 一万次，基本横向替代原有扁平化链路。

### 1.2 可能会问的问题

1. 为什么试了 SuperAPI 不行？
	上下文噪音太多、数据依赖是链式触发的
	
2. 为什么单 Agent 不够？

	我们碰到了框架设计以及模型能力上限导致的问题。通过修改提示词无法解决的问题，也就是模型上下文窗口的上限问题。试过单 Agent 循环调用，在 20 个高难度客诉上测，解决率不到 60%。链路一长就崩：超过 7-8 步，要么忘了最初要证明什么，要么被海量返回带偏。
	所以转向多智能体。不是因为"分工更清晰"，而是因为每个 Agent 有独立上下文，可以并行探索。

#### 1.2.1 上线后的收益

线上完整解决率我没有闭环数据，所以不硬报；但离线是有量化的，早期单 Agent Pass Rate 不足 60%，升级后在 100 个复杂 Case 上，核心证据覆盖率从 42% 提升到 88%，硬数据幻觉率降到 0.5% 以下。这说明复杂问题的解决质量是明显提升了。

## 高德地图 AI 打车

### 1. 说辞

我们这里链路是让模型判断应该走哪条路，比如取消订单，打车还是查订单。然后就是对应的根据用户的输入进行槽位提取，目的地、出发地、订单号等关键参数补齐。依赖模型推理服务的系统。

因为是 TOC 的服务，所以我们需要确保服务的稳定性和 RTT 要低。

为了提高响应速度：选取没有思考链的 instruct 模型 和 提示词缓存
- 对于 ToC 场景，RTT 和吞吐都很敏感，所以我们优先用更适合指令跟随、响应更快的 instruct 模型去承接主流程。同样的资源预算下，可以承接更多请求，把系统的稳定区间拉大。
- 对于参数提取，我们会选择线程池并发提取降低任务的复杂难度，会提升准确率。同时方便以后增加槽位或者进行修改的时候，不影响当前调试的模型以及其提示词。

为了应对高并发的流量：

1. 对于推理服务端的错误，我们选择精细化处理，对于部分5xx 的错误重试，对于比如并发过高，超出限制的服务进行返回错误的处理（安抚模型生成话术）。重试的时候，选择指数退避，避免成为压垮的第二波流量。
2. 对请求进行分流，我们设计了**意图路由，对于低价值请求，会有专门的话术去进行处理，防止将高价值服务给发生挤兑。**
3. 另一方面是在产品侧去进行操作，梳理出，能不走模型的操作，尽量给出快捷键。对于取消订单、确认订单，上车点，下车点、支持按钮操作，不走模型推理服务。


同时还有一些常规的操作：
1. 为了支持可观测，记录日志，错误可复现，我们会对模型的输出输出异步落库处理，这个需要开发初期就做好，然后可以去验证到底出错的步骤是先发生在哪一步。支持问题回放与 Bad Case 快速迭代。
2. 关键指标监控 + 报警
3. 采用降级策略：进行“智能盲猜”，当前位置 + 时间段常用位置。

---

后期优化，其实可以继续控制下细节，控制推理服务的调用次数，对于提取出来的槽位存放到上下文中，支持 redis 恢复，支持追加功能。

- **起请求阶段：** Netty 的一个 EventLoop 线程执行到 `Mono.zip` 时，会通过底层的非阻塞 Socket 将 3 个 HTTP 请求并发发送给 80B 模型服务端。发送完毕（耗时微秒级），**该线程立刻返回，去处理其他用户的打车请求**。此时没有任何 Java 线程在原地等待。
- **等待阶段：** 操作系统内核（Epoll）在后台监听这 3 个 Socket 的状态。
- **响应到达阶段：** 当 80B 模型的返回数据到达网卡时，内核触发 Epoll 事件，Netty 从池子中唤醒一个可用线程，读取数据并执行 `map` 中的合并逻辑。

这个对于 需求单评分会有两次大模型调用，并且项目是单体的，一次请求是会持续2、30秒。并且这个服务是强依赖推理服务的，也就是说大模型如果调用失败，或者推理服务不稳定，就会导致请求的失败。所以说这个服务需要的是健壮性。

所以我引入了状态机来解决这个问题，使用阻塞队列和数据进行配合，来实现对状态的持久化，比如从数据库拉下来是一个状态，然后给到大模型第一次请求后是一个状态。

当然更重要的是如果推理服务请求失败，经历过指数退避的三次重试后还是不行，我们就会将其设置任务停止时间，防止频繁请求对推理服务持续造成压力。到达时间后重试并且报警。

> 20/30 h100还是 h200 ，我计算是指此 200 多次请求。但是分配给我们只有同时支持 20 次请求。

所以据此设置了令牌桶算法，也就是做了一个信号量，每次请求前先-1，然后用完后 + 1。控制并发的请求。

#### 2.4.2 业务含义，需求完整度评分

**需求背景**：项目因什么业务痛点而生，解决了什么问题，预期对业务指标（如留存率、转化率）有什么影响

**指标类型**：该指标是核心指标（直接影响业务决策）、观测指标（辅助观察）还是维度（用于拆分/筛选），核心指标需说明如何衡量好坏

**业务含义**：指标的业务定义是什么——用户什么行为会影响它、系统哪个模块会反映在上面、它的数值变化代表什么业务含义

**字段来源**：数据从哪来——是用户行为埋点日志（指定日志表和字段）、还是已有维表（指定表名和主键）、还是其他数据源

**数据范围**：统计的口径是什么——统计的是哪类行为（曝光/点击/转化/互动）、哪类流量（微信/联盟）、或设置了什么过滤条件

## 3. LangChain4j 开源贡献

我提了一组 PR，都是补 tool calling 支持的。三个改动表面无关，但核心是同一个问题：**不同协议/provider 对 tool 的定义方式不同，框架应该介入多深。**

### 3.1 PR #4915 - MCP Tool Result Extractor

**问题来源**：我在使用 LangChain4j 的 MCP 能力时，发现 tool result 的解析逻辑比较固定。MCP 协议里 `CallToolResult.content[]` 是通用结构，不同 server 返回的 payload 可能不一样，但原来的实现基本只适合默认的 text content，用户很难接管自定义结果的解析。

后来我去看了源码，定位到 `langchain4j-mcp` 里的 `ToolExecutionHelper`。这个类本质上是把 MCP server 返回的 tool result 转成框架内部的 `ToolExecutionResult`，但当时普通 `content[]` 的解析逻辑写得比较死。

**做法**：我把这块固定逻辑抽成了 `McpToolResultExtractor` SPI。默认实现保留原来的 text 解析行为，原有用户不用改代码；如果 server 返回自定义 payload，用户可以通过 builder 注入自己的 extractor，接管解析逻辑。

**trade-off**：扩展点开在哪。太底层泄漏实现细节（比如 `ArrayNode` 不能暴露到 SPI，以后换 JSON 库用户代码全挂）；太上层用户写太多代码。得卡在协议稳定层和实现细节层之间。

### 3.2 PR #4955 与 #5015 — 两个 server tools PR，相反的策略

OpenAI Responses API 里 tools 分两类：function tools（用户定义的，模型调用后由业务侧执行，再把结果传回模型）和 server tools（平台托管执行的内置工具，比如文件搜索、代码执行等）。后者不需要业务侧自己实现调用回填，但响应里会出现对应的工具调用事件和结果。框架当时只支持 function tools，server tools 相关的流式事件会直接丢失。

我分别给官方实现和第三方兼容实现（DeepSeek/Qwen 等）补了这个能力，但两个 PR 用了完全不同的策略。

**PR #4955 官方实现**：

这个模块用的是 OpenAI 官方 Java SDK，SDK 里已经有 `Tool` 等类型。我做了三件事：

1. 在请求参数类里加了 `serverTools` 字段，类型直接用了 SDK 的 `List<Tool>`。构建请求时，把用户传的 function tools 转成 SDK 的 `FunctionTool` 格式，和 server tools 合并到一个列表，通过 `paramsBuilder.addTool(tool)` 加进去，SDK 负责序列化。
2. 流式响应解析里识别 `server_tools_call` 类型的 SSE 事件。它和普通的 function call 不是同一类输出，需要在解析器里单独处理——每个 chunk 做状态累积，事件结束时拼出完整对象，再把相关调用信息暴露出来。
3. 在响应元数据类里加了 `rawResponse()` 方法，返回 SDK 的 `Response` 对象。框架没封装的字段用户可以直接从原始响应里取。

**PR #5015 第三方兼容实现**：

这个模块没有用官方 SDK，是自己发 HTTP、自己用 Jackson 解析 JSON。我做了两件事：

1. 在请求参数类里加了 `serverTools` 字段，类型是 `List<Map<String, Object>>`，不是强类型。构建请求时，先把 function tools 转成标准 OpenAI JSON 格式（`type: function, function: {name, description, parameters}`），然后把 server tools 的 Map 列表直接 `tools.addAll(parameters.serverTools())`，不做任何转换，Jackson 直接序列化发出去。
2. 响应解析那边不需要改——第三方 provider 通常把 server tool 的调用结果当作普通 tool_call 返回，框架已有的解析逻辑能直接处理。

**trade-off**：

问题不是强类型和弱类型哪个更好。是维护成本谁来付。官方 SDK 的 `Tool` 类型是 OpenAI 维护的，schema 变了 SDK 会跟着更新，框架升级 SDK 版本就行——成本 OpenAI 付了。但第三方 provider 格式没标准、随时变，如果框架用强类型去接，每多一个 provider 或者 provider 改一次格式，你都得改代码，成本框架自己扛，而且线性增长。所以用 Map 透传，让用户自己负责格式兼容，框架保持中立。

同一个思路也体现在 `rawResponse()` 上——框架不可能预见所有用户想拿的字段，provider 临时加个 `debug_info` 什么的你没法提前知道，与其追着加 getter，不如把原始响应暴露出去，用户自己取。

### 3.3 面试讲述脚本

> 我在使用 LangChain4j 的 MCP 能力时，发现 tool result 的解析逻辑比较固定，用户很难接管自定义结果的解析。后来我去看了源码，定位到 `ToolExecutionHelper` 这条链路，发现它内部对 `content[]` 的处理基本是写死的，主要适配默认的 text content。
>
> 我后面提的这个 PR，核心就是把这块固定逻辑抽成一个可扩展的 SPI，也就是 `McpToolResultExtractor`。这样默认行为保持不变，原来的用户不用改代码；但如果 MCP server 返回的是自定义 payload，用户就可以通过 builder 注入自己的 extractor，接管解析逻辑。
>
> 这不是一个特别大的功能开发，但我觉得它比较能体现框架开发里的一个关键点：不是所有协议差异都适合硬编码在框架里，合适的时候要把边界收住，通过扩展点把灵活性留给用户。

> 同样的思路也体现在我后面那两个 server tools PR 里。官方 OpenAI API 我用强类型去接，因为有 schema 承诺；第三方兼容 provider 我用 Map 透传，因为格式不稳定，框架不应该替上游承担无限兼容成本。
