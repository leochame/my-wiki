# 一、面试怎么说


我想要从两个方面去阐述我在腾讯的实习，第一个方面是

面试官您好，我在腾讯实习期间，主要负责一个 ChatBI 相关的项目。简单来说，就是让业务同学能用自然语言转换为 JSON 格式，然后再解析 JSON，最终查询数据、返回图表。

我的核心工作，就是利用大模型技术，从需求单上来我们核心知识库的数据质量以及补充业务口径。

这个项目旨在让运营、算法等业务同学能用自然语言直接查询数据，提升数据分析效率。

我加入时，项目已有一个基础的Text2SQL模型，但效果不佳，用户提问的准确率很低。从三月份开始，我们对系统进行了全面的升级重构，我主要负责和参与了以下几个关键模块的优化工作，旨在解决两个比较核心的问题：**语义理解不准**和**模型能力不可控**。

第一个挑战，是解决语义理解的精准性问题。我们专门做了一个语义澄清模块去处理语义理解的精确性问题。这个是结合 RAG 去做的。这里其实有些复杂，我放在最后再补充。

但是在实际落地的过程中，我们发现，召回的准确率受限于知识库内容的区分度，知识库的完整度。内容区分度的话，其实我的工作主要有：

1. **对领域知识库的内容进行完善**：

- **从代码中挖掘事实**：为了确保指标定义的绝对精确，我们放弃了依赖不靠谱的旧文档。我参与设计了一个方案，通过**正则表达式从生产环境的Scala代码中，自动化地抽取出指标的计算逻辑、来源表和字段**。然后，利用LLM将这些结构化信息总结成自然语言描述，构建了一个高可信度的指标知识库。
- **从需求中提炼业务**：对于业务流程和场景描述，我们通过接口拉取需求管理平台的历史需求单。并引入一个**LLM Agent对需求单的质量进行自动化评分**，将低分原因推送给相关同学，倒逼业务方提升需求文档的质量，为我们提供了更优质的知识源。
- **梳理近似指标**：我还参与设计了一个Agent，它利用LLM对数仓中名称或定义相似的指标进行**分组、打标签，并解释它们在计算逻辑和适用场景上的差异**，甚至对一些冗余或不合理的指标提出下线合并建议，极大地降低了用户选择指标的难度。

**第二个挑战，是解决大模型的幻觉和持续迭代问题。** 即使有了好的知识库，LLM自身的不确定性也需要被约束。

1. **抑制模型幻觉**：我们通过设计非常严格的**提示词模板（Prompt Engineering）**，强制模型必须基于我们提供的、带有编号引用的上下文来生成SQL，并在回答中注明信息来源。这有效地减少了模型捏造不存在的表或字段的问题。

2. **建立模型迭代的反馈闭环**：
- **主动澄清与样本收集**：我们在系统中加入了“澄清反问” 模块。当用户问题不明确时，模型会主动追问，澄清意图后再执行。同时，我们会记录所有失败的Case和用户反馈。
- **周期性精调 (Fine-tuning)**：我们会定期将收集到的错误样本（特别是人工修正后的正确SQL），整理成精调数据集，对模型进行**周期性的Fine-tuning**。这对于让模型理解我们业务特有的术语，以及那些“定义相似但代码实现不同”的细微差别至关重要。
- **分钟级热修复 (ICL)**：考虑到精调的周期是周级，对于线上紧急且重要的问题，我们建立了一套**ICL（In-Context Learning）的快速修复机制**，通过在Prompt中动态添加少量示例，可以在分钟级别修正模型的行为，保障了线上服务的稳定性。

2. 讲清楚“为什么要做”，展现你对业务的理解能力。

但是实际落地的时候有几个严重的问题，其中包括：

第一个问题，用户的问题模糊、用户问的问题不全。这个我们就专门做了一个**意图澄清**模块去进行处理。

第二个问题，召回的成功率低。

模型的召回成功率特别低，经常答非所问或者找不到数据。我们深入排查后发现，**问题的根源出在了知识库上**：

1. 大量的字段名和语义相似。指标的定义模糊，内容不全。而我们的指标的业务口径，是产品、运营、算法团队同学提交的‘需求单’中描述的，由需求方定义的。
2. 但这些需求单的质量参差不齐，普遍存在背景缺失、指标定义模糊、分析维度不明确等问题。这样也就导致了，指标的业务口径内容不完整。这样低质、模糊的描述，没有办法来作为我们的知识库的原始语料。给大模型提供了很多错误、矛盾的‘原材料’，它自然无法准确地理解和检索，召回的结果特别差。

我的任务就是来给 ChatBI 的知识库，以及数据治理专项提供支持。数据治理专项就是对部分字段合并重复、并且下线部分内容。

**来提升需求单的质量，确保所有进入知识库的元数据都是完整的、经过审核和净化的。以及提取出需求单中的业务口径，**提供给 ChatBI 以及数据治理专项使用**。**

2. **怎么做呢？**

“我设计并落地了一套**基于大模型的自动化评审与反馈闭环系统**。整个流程可以概括为三步：‘主动发现 -> 智能分析 -> 闭环反馈’。”

为了实现这个目标，我设计并落地了一套基于 LLM 的自动化评审与反馈闭环系统，整个流程可以概括为‘主动发现 -> 智能分析 -> 闭环反馈’

- **主动发现：** 我开发了一个定时任务，通过 HTTP 接口增量拉取最新的需求单，实现对数据源头的持续监控。
- **智能分析：** 这是系统的核心。我没有用简单的规则，而是把 LLM 作为我们的 **‘智能质检员’**。我设计了 **结构化的 Prompt**，让 LLM 扮演一个严谨的‘数据专家’角色。它会首先判断需求单是否包含新增指标，然后对每个新增字段，从业务口径、技术口径等多个维度进行结构化打分和分析，并以 **JSON 格式**输出评审报告。这种**清单式、分步式**的 Prompt 设计，极大地约束了模型的**‘幻觉’**，让输出变得可控和精确。
- **闭环反馈：** 系统会自动将 LLM 的评审报告以评论形式写回到需求单下方，并通过企业微信机器人@相关的需求提出人。当他们修改后，还可以通过机器人触发一次**‘复审’**，形成了一个完整的质量提升闭环。

---

**升华：挑战与工程化思考**

然而在开发的时候我注意到了几点问题：

1. 这是一个长链路异步请求问题，中间服务请求失败怎么办，服务突然宕机怎么办？
2. 我们请求大模型的时候，有时候请求失败，可能是算法服务出了问题，单调的重试其实是不能解决问题的
3. 另外我们在设计的时候，就遵循着这样一个设计原则：必须要保证 至少一次 成功处理的语义。

这是一个**异步、长链路、多外部依赖**的系统，任何一步超时或失败都可能导致整个任务中断。为后端开发，我必须在**单体应用**且**不能引入额外中间件**的限制下，保证系统的健壮性和可靠性。

- **轻量级任务引擎**：为了解决这个问题，我没有引入复杂的外部中间件，而是巧妙地在单体应用内部设计了一个**轻量级的任务处理引擎**。我用 **任务状态表**持久化任务状态，并结合 Spring 的 `ApplicationRunner`，实现了**故障后的‘断点续传’**。这种设计既满足了‘至少一次（At-Least-Once）’的处理语义，又避免了引入外部中间件带来的高昂成本和复杂性。
- **精细化外部调用**：针对 LLM 这种响应时间不确定的服务，我放弃了传统的 `RestTemplate`，选用了 `**WebClient**`。通过配置 **精细化的超时策略**（如连接超时5秒，读取超时90秒）和带**‘抖动’的指数退避重试**，防止了‘惊群效应’。如果多次重试仍失败，系统会标记任务状态并告警，实现了**‘任务级别的熔断’**。

当然，实现这个长链路的自动化流程挑战不小。因为我们是单体应用，又不能引入额外的中间件，所以**系统的健壮性和可靠性**是我要解决的首要难题。

“最大的挑战是，这个链路长、且依赖外部HTTP调用（LLM、需求平台），任何一步超时或失败都可能导致整个任务中断。如果粗暴地重试，可能会导致重复评论。为了解决这个问题，我当时没有选择简单的异步调用，而是在应用内部设计并实现了一个**轻量级的、基于状态机的任务处理引擎**。”实现至少执行一次的任务处理能力和故障自愈能力

“具体来说：

- **状态与任务解耦**：我设计了一张核心的‘任务状态表’，每个需求单的评审都是一个任务，有‘`RECEIVED`, `ANALYZING`, `ANALYZED`, `EVALUATING`, `EVALUATED`, `SUCCESS`，`反馈``FAILED` 等状态。**状态的持久化是保证任务不丢失的基石**。
- **用内存队列实现异步化**：我利用Java的 `BlockingQueue` 在应用内部构建了多个内存队列，每个队列对应状态机的一个关键步骤（如‘待分析队列’、‘待反馈队列’）。上一步完成后，更新数据库中的任务状态，然后将任务ID投入到下一个队列。**这样做既实现了异步解耦，又避免了引入外部中间件的复杂性**。
- **断点续传与故障自愈**：这套架构最妙的地方在于它的**故障恢复能力**。我利用了Spring的 `ApplicationRunner`，它能确保在整个应用完全启动后执行一段逻辑。这段逻辑就是去扫描数据库，**捞出所有处于‘中间状态’（比如‘分析中’）的任务，然后将它们重新投递到对应的内存队列中**。这样一来，哪怕应用因为部署或意外宕机，重启后也能自动从中断的地方继续执行，保证了每个任务**‘At-Least-Once’（至少一次）** 的处理语义。”
- **精细化外部调用**：在调用LLM这种响应时间不确定的服务时，我放弃了传统的 `RestTemplate`，选用了Spring的非阻塞客户端 `WebClient`。这让我可以非常方便地做到**精细化的超时控制（比如连接超时和读取超时分开设置）和灵活的重试策略**，防止慢请求拖垮整个系统的处理能力。

**最终优化结果以及后续迭代**

- **需求单质量大幅提升**：需求单的“一次性通过率”（即无需开发反复沟通就能开发的比例）从系统上线前的约 **40% 提升到了 65%**。新提交需求单的平均“信息完整度”评分**提升了 30%**。
- **沟通效率显著提高**：它将过去需要数据开发花费大量口舌去“追问”的模糊点，前置到了提交阶段由机器自动完成。沟通模式从低效的“我看不懂你的需求”，转变成了高效的“机器人提醒您，第 X 节缺失 Y，请补充”，极大地节约了团队的人力成本。

这一层是展示你对系统长期演进的思考，构建一个能自我优化的系统。**建立反馈的反馈机制 (Feedback on Feedback)**：在LLM生成的每一条评审意见旁边，增加一个简单的“**这条建议是否有用？(****👍****/****👎****)**”按钮。让需求方可以对我们系统的评审质量进行评价。

**构建自我优化的闭环**：

- 收集上述的用户反馈数据。
- 将那些被标记为“有用(👍)”的建议，以及需求方根据建议修改后的高质量文本，**自动整理成新的高质量Fine-Tuning样本**。
- 将被标记为“没用(👎)”的建议作为负样本。
- 定期用这些新样本去**微调我们的评审大模型**。

# 三、附加问题

### 1. 问题一：这个系统你怎么设计的这么复杂？

**回答策略**：不要直接否认“复杂”，而是承认并解释“复杂”背后的价值。把“复杂”重新定义为“健壮”和“有远见”，展示你对生产环境的深入思考。

**你可以这样说：**

“您提的这个问题非常好，也正是我在设计过程中反复思考的核心。坦白说，这个系统的**第一个版本（V1）其实非常简单**。”

“按照我导师最初的要求，我实现的就是一个‘评估脚本’：接收一个需求ID，串行调用大模型API，然后打印出评估结果。这个版本代码可能只有几十行，非常直接，用来做功能验证是完全没问题的。”

“但在我完成V1，并尝试用它处理一些真实的历史数据时，我发现了几个**生产环境中无法回避的致命问题**：”

1. “**第一，可靠性差。** 这是一个长链路，调用LLM、调用需求平台API，任何一次网络抖动或服务超时，整个任务就失败了。失败后没法重试，数据就丢了，对于一个数据治理系统来说这是不能接受的。”
2. “**第二，扩展性弱。** 如果未来我们想在‘评分’和‘回写评论’之间增加一个‘存入数据库’的步骤，我就得去修改核心代码，很容易改出新问题。”
3. “**第三，性能瓶颈。** 串行处理的效率太低，如果要批量处理积压的历史需求单，会非常非常慢。”

“正是因为预见到了这些问题，我才主动把系统**从一个脆弱的‘脚本’，演进成了一个更健壮的‘服务’**。现在您看到的这套基于状态机和阻塞队列的架构，看似复杂了，但它带来的好处是巨大的：”

- “**状态机+持久化**，解决了断点续传和任务不丢失的问题，保证了**可靠性**。”
- “**环节之间用队列解耦**，未来想增加或修改某个处理步骤，就像插拔一个零件一样简单，保证了**可维护性**。”
- “**异步处理**，为未来的性能扩展留出了空间。”

“所以，这个‘复杂’其实是为了**用前期的设计投入，换取系统在生产环境下的长期稳定和低维护成本**。我认为对于一个要长期运行的数据治理服务来说，这笔‘投资’是非常值得的。”

### 2. 问题三：为什么使用了 RPC 而没有使用 HTTP？

“**第一，也是最重要的一点，是出于‘系统集成’的需要。** 我负责的这个自动化服务，它的核心职责之一是**与多个已经存在的、成熟的内部平台进行交互**，比如‘需求管理平台’。这些平台为了保证通用性和稳定性，向上层应用或第三方工具开放的都是**标准的 HTTP RESTful API**。”

“我们作为调用方，使用 HTTP 是与它们集成的最直接、最标准的方式。如果想用 RPC，反而需要对方平台为我们这个小工具专门开发和暴露 RPC 接口，这在跨团队协作中几乎是不可能的，也违背了平台化的设计初衷。所以，**不是我们不想用RPC，而是我们交互的目标服务，它提供的是HTTP接口。**”

“**第二，这完全符合我们项目在‘快速验证（PoC）’阶段的目标。** 当时我们的首要任务是快速开发出原型，来证明‘用LLM赋能数据治理’这条路是走得通的。HTTP + JSON 的技术栈非常成熟，生态极其丰富，调试起来也非常方便——一个简单的 `curl` 命令或者 Postman 就能测试接口。”

“这让我们能把全部精力都聚焦在**核心的业务逻辑和模型效果调优**上，而不是耗费时间去处理 RPC 的桩代码（Stub）、服务发现和复杂的环境配置。可以说，选择HTTP，是我们为了**‘敏捷’和‘速度’**做出的正确取舍。”

“**第三，这个技术选型也符合我们对它‘独立后台工具’的架构定位。** 它不是一个核心交易链路上的高性能微服务，它的特点是**低频调用、异步执行、长耗时**（大部分时间都在等LLM返回结果）。”

“在这种场景下，RPC 带来的微秒或毫秒级的性能优势，相比于几十秒的 LLM 调用耗时，是完全可以忽略不计的。反而，HTTP 带来的**松耦合、易于维护、易于被网络策略（如防火墙）管理**等好处被放大了。因此，我们认为没有必要为了一个后台提效工具，就把它和公司内部复杂的 RPC 治理体系（比如服务网格、统一网关）进行强行绑定，增加不必要的复杂度。”

### 3. 问题四：为什么没有纳入 Main 库

“您说的很对，这个模块在当时确实是独立于主代码库之外的。这主要是因为，**我们这个项目在当时是一个创新性的技术预研（或称PoC，Proof of Concept）项目**。”

“当时团队希望探索利用大模型来自动化和标准化内部的数据治理流程，这是一个全新的方向，存在很多不确定性。为了**快速迭代和验证这个方案的可行性**，我们决定不立即将它整合进已经非常庞杂和稳定的主代码库中——因为那样会让我们的开发和调试速度受限于主站的发布周期。”

### 4. 问题五： 数据量过多怎么办？

1. **检索性能下降 (Performance Degradation)：**向量索引体积巨大，最近邻搜索（ANN）的计算量剧增，导致检索延迟（Latency）显著升高，无法满足实时交互的需求。
2. **检索精度降低 (Accuracy Degradation)：**知识库中包含了大量相似但非相关的“噪音”文档。检索时，这些噪音文档很容易被错误地召回，导致返回给LLM的上下文（Context）质量变差，最终影响生成结果的准确性。这就是所谓的“大海捞针”问题。
3. **运维和更新成本飙升 (Maintenance Overhead)：**如此庞大的知识库，其索引的构建、更新、版本管理都变得极其复杂和耗时。一次全量索引重建可能需要数小时甚至数天。
4. **存储和计算成本增加 (Cost Increase)：**海量的原始文本和向量数据需要巨大的存储空间。同时，索引构建和检索查询需要消耗大量的CPU/GPU和内存资源。解决这个问题需要一个系统性的方法，可以从**检索优化**、**知识库优化**和**系统架构**三个层面入手。

---

怎么解决？

1. 优化检索（R）本身，这是最直接的优化层面，目标是“更快、更准”地捞取信息。

- **索引策略优化**：

- **量化 (Quantization)**: 使用乘积量化（PQ）等技术压缩向量大小，牺牲少量精度换取巨大的存储和速度优势。这几乎是海量向量检索的标配。
- **分层索引 (Hierarchical Indexing)**: 比如先对文档的摘要（Summary）或聚类中心建立一个小的“入口索引”，快速定位到相关文档范围，然后再在小范围内进行精确检索。例如，先检索章节标题，再检索章节内的段落。

- **混合搜索 (Hybrid Search)**：将传统的关键词搜索（如BM25）与向量搜索相结合。关键词搜索能精准匹配专有名词和术语，向量搜索能理解语义。两者结合，取长补短，能显著提升在复杂知识库中的检索精度。
- **查询重写/转换 (Query Rewriting/Transformation)**：在检索前，先用LLM对用户的原始问题进行分析和改写，生成更适合检索的、更明确的查询语句，甚至生成多个子问题分头检索，再将结果综合。

2. 优化知识库（K）内容，这是从源头解决问题，目标是提升知识库的“信噪比”。

- **智能分块 (Intelligent Chunking)**：放弃固定长度分块。采用基于语义的分块策略，例如按段落、章节、或者使用`LlamaIndex`等框架中的`Semantic Chunker`，确保每个Chunk都是一个语义完整、独立的知识单元。
- **知识蒸馏与分层 (Knowledge Distillation & Layering)**: 为每个文档或长篇章节生成高质量的摘要，并将摘要向量化。检索时可以先检索摘要层，快速筛选。
- **知识图谱 (Knowledge Graph)**: 提取文档中的实体（Entities）和关系（Relations），构建知识图谱。对于事实性、实体性的查询，直接查询图谱可能比向量检索更高效准确。
- **数据清洗**：在入库前进行严格的数据去重、去除低价值信息（如免责声明、页眉页脚等），从源头上减少噪音。

3. 架构层面的优化 (System Architecture)

- **路由 (Routing) / 知识库联邦 (Federated Search)**:

- **核心思想**: 不要把所有鸡蛋放在一个篮子里。
- **实现**: 将庞大的知识库根据主题、业务领域或数据来源切分成多个小的、独立的子知识库。建立一个“路由层”（可以用一个轻量级的分类模型或LLM），先判断用户问题属于哪个领域，然后仅在对应的子知识库中进行检索。
- **优势**: 大幅缩小单次检索的范围，性能和精度都得到提升，且各子库可独立更新，降低了运维复杂度。这类似于后端架构中的“微服务”思想。

- **分布式向量数据库**：使用专为海量数据设计的分布式向量数据库，如 Milvus, Weaviate, Pinecone 等。它们提供了水平扩展、数据分片、负载均衡等能力，是解决性能和存储瓶颈的工业级方案。
- **多级缓存 (Multi-level Caching)**：对于高频查询及其检索结果进行缓存。可以设置不同粒度的缓存，如查询-文档ID缓存、查询-最终答案缓存等。这是典型的后端性能优化手段。

9. 讲讲 WebClient

10. 当使用 `WebClient` 时，它底层的网络通信框架（通常是 Netty）有自己专门的 **I/O 线程池**（通常称为 Event Loop Group）。这个线程池里的线程数量很少（通常是CPU核心数的1倍或2倍），它们是高度优化的“交通警察”，专门负责监听网络端口、接收和发送数据包。
11. 当一个 HTTP 响应从 LLM 服务返回时，默认情况下，是 Netty 的一个 **I/O 线程**负责接收数据，并开始执行您的回调逻辑（比如 `.onSuccess()`, `.onError()`, `.map()` 等操作）。
12. **I/O 线程是“稀有资源”**：它们是整个异步系统的脉搏。一个 I/O 线程需要同时处理成百上千个并发连接的网络事件。
13. **阻塞的致命后果**：我的回调逻辑需要做什么？它可能需要解析复杂的JSON，**最重要的是，它需要去写数据库来更新任务状态**。传统的 JDBC 数据库操作是**阻塞的**。如果我把这个阻塞的数据库写入操作放在 I/O 线程上执行，那么这个 I/O 线程就会被卡住，直到数据库返回结果。
14. **系统雪崩**：在这个 I/O 线程被卡住的期间，它无法去处理任何其他的网络事件。如果我的并发量稍大一点，导致所有几个宝贵的 I/O 线程都被我的数据库操作卡住了，那么整个应用的网络层面就会**完全瘫痪**，无法接收新的请求，也无法处理其他已发出请求的响应。这就是灾难性的后果
15. ……因此，一个小的消费者线程池就能发起海量的并发请求。但这里还有一个关键细节，就是**回调逻辑的线程隔离**。
16. 为了防止业务逻辑（比如阻塞的数据库操作）拖垮核心的I/O网络线程，我利用了响应式框架中的 `publishOn` 操作符。它能将网络响应的处理，从**高性能的I/O线程池**，安全地切换到**专门用于执行业务逻辑的线程池**。这种线程模型的精细化分离，确保了即使在处理复杂回调时，整个应用的I/O核心依然能保持极高的吞吐量和响应速度，这样一来，**I/O 线程在完成了它的本职工作（接收网络数据包）后，就立即被释放了**，回去继续处理其他网络事件，整个系统的响应能力得到了保障。
17. 让我们来推演一下当 Pool A 和 Pool B 合并成一个共享线程池（我们称之为 `Pool_Shared`）后，在遇到压力时会发生什么：
18. **系统正常运行**：

- `Pool_Shared` 的一部分线程（比如T1, T2）作为消费者（角色A），从 `BlockingQueue` 中取出任务，调用 `WebClient` 发起请求。
- 请求的响应回来后，回调逻辑被 `publishOn` 调度，任务被扔回 `Pool_Shared`。
- `Pool_Shared` 的另一部分线程（比如T3, T4）作为业务处理器（角色B），执行这些回调任务（写数据库等）。
- 一切看起来很和谐。

10. **外部服务（LLM）开始变慢**：

- LLM 服务的响应时间从 1 秒变成了 30 秒。
- 这意味着，我们的回调任务（角色B）执行时间也会相应拉长，因为它们需要等待响应数据。

11. **灾难的开始：线程耗尽**：

- 假设 `Pool_Shared` 的大小为 50。
- 由于 LLM 变慢，大量的请求响应开始堆积。`Pool_Shared` 中的线程，一个接一个地被分配去执行这些漫长的回调任务（角色B）。
- 很快，`**Pool_Shared**` **的全部 50 个线程，都卡在了执行角色B的任务上**——它们都在等待 LLM 的响应，或者在执行响应回来后阻塞的数据库操作。

12. **系统锁死：消费者饥饿（Consumer Starvation）**：

- 此时，`BlockingQueue` 里可能还堆积着成百上千个等待被处理的新需求单。
- 但是，`**Pool_Shared**` **里已经没有任何一个空闲线程，可以去扮演消费者（角色A）的角色了！**

- 结果就是：**系统无法再从队列里取出任何新任务来处理。** 整个处理链路从源头上就被卡死了。尽管机器的CPU、内存都很空闲，但我们的应用程序却因为线程资源被“错误地”全部占满，而陷入了停滞。

我们之前是有过实现的，但是做了个最基础的版本，会回答关于这个问题的查询 sql，是一个经典的 Test2Sql 的实习项目。但是效果一般，所以我们从三月份开始对整个 ChatBI 进行了升级。

之前 ChatBI 实现选择了 Test2Sql的技术路线，虽然Test2Sql技术路线整体能力的天花板更 高，但是对于大模型来说生成准确的sql也会更加困难。另外，鉴于经营数仓整体的 指标中台 建设也愈加成熟，用户取数分析也多数集中在通用探索分析场景，因此，我们决定尝试 text2dsl的路线，实现在通用探索分析场景下的自然语言取数能力。

由于之前我们的这个平台本身的探索分析本身就有 DSL 解析，他这个的实现是通过拖拽实现一个 DSL 返回给后端，进行权限校验等流程后呈现给用户。所以我们现在做的其实是将用户的查询，转换为 DSL，然后 DSL 转换为 SQL。这个就大幅度减少了 LLM 的自由发挥空间，从自动生成 SQL 变成了做模板填空题。

但是这也面临着几个挑战：

1. 用户的问题是比较天马行空的，语义其实是比较泛化的
2. 提问的时候的条件并不是很充足
3. 然后问的词条也不足够清晰。

所以我们是通过多轮对话的形式，补充上用户的完整询问语句。如果用户第一次问的不够清楚，我们将会返回并且配合查询到数据库，以及数据库的字段。

为了解决第一个问题，我们会在通过意图澄清模块与用户交互，补充完整用户意图，并且附加上相关的知识库系统，构建完成上述输入后，由 FunctionCall Agent 调用 DSL 生成工具。

这个意图澄清 Agent，这个 Agent 包含多轮对话改写 Agent ，意图澄清，关键词提取，关键词提取和澄清选项生成。关键词提取是提取出业务概念关键词列表。最后是澄清选项，在歧义的情况下选择三条最高概率的，在无歧义的时候选择一条就可以。

我们在实践中发现他生成的时候，发现如果是一下子，全量生成，大模型容易出现幻觉问题，我们就采用了，一步步的喂给 LLM，先填充指标，再填充维度，再补充条件。这样子其实就是说，你对大模型的要求更加严格了，一步步的生成，效果就提上来了。然后调优毕竟是要基于效果进行的，目前来看效果表现是很不错的。

另一个就是大模型的幻觉问题，我们对于幻觉问题一方面通过元数据信息字段，维度取值，专家黑话库等，构建结构化知识库。

但是普通的知识库在实践过程中，发现在多个维度字段语义近似的时候，召回的信息也非常差，这个其实也可以理解，如果大模型在生成 Token 的时候，候选的几个 Token 概率都基本一致的情况下，选谁都可以的情况下，这是最容易出错的。

所以说这才是最关键的，也就是用户语义这块，如果这里出错了，其实就整个下游链路都会失效。

1. 这边面临着，一个主要是 LLM 的幻觉问题：其实在这里，你哪怕配合上语义资料，LLM 也会出现幻觉问题，所以可能给出的表格或者字段是错误的，或者根本不存在的。

现在的做法是，控制提示词模版，说必须基于以下材料，然后对材料标注123，再注明来自哪里的 123。

2. 第二是，RAG 严重依赖语义库的质量，既要对切段落的时候，严格控制，认为划分。还要补充完整语义库，行业黑化库，比如：美妆行业对应着其实包含：本土美妆、国际美妆。泛金融包含着贷款，这种语义库的问题。
3. 行业黑话库，暂时依靠后续在使用的时候，收集问题，然后人为的去补齐
4. 对于语义库的出现，其实，我们做的就是通过需求单和变量名的产生逻辑去进行的。变量名的产生逻辑，我们是通过对代码文件进行正则表达式匹配，然后递归的获取到，再给大模型，让大模型总结后生成文本后落库，完成的。对于指标的出处，这个要求必须十分精确，所以我们配合生产代码进行的，主要是 Scala 代码。
5. 对于需求的话，主要是之前的需求单的质量参差不齐，然后我们通过 LLM 对需求单的完整性评分，再调用接口，推送到评论区。首先我们是从需求管理平台，拉取需求，然后对需求单喂给 LLM 进行评分。针对 LLM 的返回结果，我们存储在本地数据库，进行更新。

这里就延伸出了一个新的 agent：数据字典缺少的相关业务描述和横向对比，进行补齐，让普通用户理解差异，提高指标的使用门槛。降低无效指标，重复指标。利用大模型对 数仓近似指标分组梳理，近似指标添加场景标签，解释彼此差异。不合理的近似指标合并下线。
