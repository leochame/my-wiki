# 外贸客户开发：海关编码与行业邮件触达

## 核心想法

针对某一类出口商品，先确定对应的海关编码（HS Code），再用这个编码检索真实发生过出口的企业，把它作为潜在客户池。对企业做基础背调后，使用公司邮箱向纺织等相关行业从业者进行定向邮件触达，验证是否存在合作需求。

## 可能的工作流

1. **定义商品范围**
   - 明确产品名称、材质、用途、规格和目标国家。
   - 核对适用的 HS Code；如果存在多个候选编码，记录判断依据，不把编码当作绝对准确的产品标签。

2. **按编码发现企业**
   - 从合法、可追溯的海关/贸易数据源筛选使用该编码出口的企业。
   - 记录企业名称、出口国家、时间范围、频次、数量或金额（如果数据源提供）以及数据来源和抓取日期。
   - 优先保留近期、持续出口且产品描述与目标商品匹配的企业。

3. **企业背调与排序**
   - 核验官网、产品目录、公司注册信息、目标市场、联系人职能和公开联系方式。
   - 排除无法确认主体、产品不匹配、明显停业或联系方式来源不明的记录。
   - 给每家公司标注匹配理由、优先级和待验证假设，而不是只按出口次数排序。

4. **定向邮件验证**
   - 针对具体企业和岗位写短邮件：说明信息来源背景、可能的业务关联、能提供的价值和一个低成本下一步。
   - 只使用公开且适合商业联系的邮箱，遵守发送地和收件地的反垃圾邮件、隐私和个人信息规定。
   - 保留退订方式、发送记录和抑制名单；控制发送频率，避免无差别群发或伪装成个人邮件。

## 最小验证实验

- 选一个明确的纺织品类和一个 HS Code。
- 收集 20 家近期出口企业，人工核验其中至少 10 家。
- 写 2 个不同价值主张的邮件版本，每个版本发送给一小批高度匹配的联系人。
- 观察有效送达率、回复率、正向回复率、退订/投诉率和进入下一步沟通的比例。
- 根据回复内容修正产品定位、目标岗位和筛选条件，再决定是否扩大样本。

## 需要先确认的问题

- 目标商品的具体定义和候选 HS Code 是什么？
- 可合法使用、且覆盖目标市场的贸易数据源是什么？
- 我们真正要提供的产品/服务价值是什么，适合找采购、供应链还是其他岗位？
- 发送主体、邮箱域名、退订机制和数据留存方式是否已经准备好？

## 风险与边界

- HS Code 可能被误报、过于宽泛或在不同国家有细分差异，必须结合产品描述和官网信息复核。
- 出口记录不等于当前有采购需求；它只是线索信号，不能直接作为营销许可或事实结论。
- 不购买或拼接来源不明的个人邮箱名单，不绕过访问控制，不发送无法退订的高频营销邮件。
- 对公开数据和联系人信息记录来源、用途、保留期限和删除请求处理方式。

## 自动化实现方案

## 开发目的与技术路线

### 开发目的

使用 Python 开发一个面向外贸客户开发的 AI 线索系统，把“按 HS Code 找企业、企业背调、公开邮箱发现、线索评分、邮件草稿和结果跟踪”串成可重复执行的工作流。系统的目标是减少人工搜索和整理时间，提高高匹配线索的发现效率，而不是制造无差别群发工具。

系统应具备以下特征：

- 每个企业和联系人都有来源证据、抓取时间和处理状态；
- AI 输出可解释、可复核，原始数据不被模型结果覆盖；
- 发送前有人工审核、频率限制、退订和抑制名单；
- 数据源、模型、邮箱服务和邮件服务可以替换；
- 所有任务、判断、发送和删除请求都有审计记录。

### Python 应用分层

```text
数据接入层       海关/贸易数据、官网、企业目录、邮箱验证服务
标准化与存储层   清洗、去重、主体合并、证据和状态存储
AI 分析层        产品匹配、公司摘要、联系人角色、线索评分、邮件草稿
工作流编排层     重试、队列、人工审核、定时任务、发送闸门
接口与报告层     CSV/数据库导出、审核页面、指标和审计日志
```

### Claude Code/Agent SDK 与 LangChain 的定位

- **Claude Code/Agent SDK**：适合把网页读取、文件处理、数据库查询和人工确认组织成具备工具调用能力的任务代理。具体 SDK 名称和 API 以当前官方版本为准，模型密钥只从环境变量或密钥管理器读取。
- **LangChain**：适合把检索、结构化输出、模型切换、重试、记忆和多步骤链路封装成可测试的组件；需要更复杂的状态流转时，可在 LangChain 生态中选择图式工作流组件。
- **组合方式**：底层业务逻辑保持普通 Python 模块，数据模型、评分规则、抑制名单和发送闸门不绑定某个模型框架；SDK 或 LangChain 只负责调用工具和编排步骤。这样可以先用一种方案验证，再替换另一种方案，不重写核心数据层。

### 建议的第一版工程边界

第一版只实现“导入 20 家企业 → AI 背调和评分 → 生成邮件草稿 → 人工审核导出”，暂不接入自动发送。确认评分质量和邮件内容后，再增加邮箱验证、定时任务和小批量发送。这样可以先验证业务价值，再承担真实发信和个人信息处理的运营风险。

### 1. 数据源获取

按优先级选择数据源：

1. 目标国家海关或统计部门的公开数据、下载文件和官方 API。
2. 有明确授权和使用条款的商业贸易数据库；购买前确认是否允许导出、再加工和销售线索用途。
3. 企业官网、展会目录、行业协会名录和公司注册信息，用于补充企业主体与产品描述。

不要把搜索引擎结果页或登录后页面当作稳定数据接口，也不要绕过验证码、访问控制或 robots 规则。每条记录保存 `source_url`、`source_type`、`retrieved_at` 和授权/条款备注。

### 2. 线索管道

可以用 n8n、Make 或定时脚本编排以下步骤，数据库可先用 SQLite/Postgres：

```text
HS Code + 国家 + 时间范围
        -> 导入贸易记录
        -> 标准化公司名/域名
        -> 去重与主体合并
        -> 官网和产品描述抓取
        -> AI 判断产品匹配度
        -> 规则 + AI 综合评分
        -> 人工审核队列
```

AI 适合做产品描述分类、公司名归一化、官网内容摘要、采购角色判断和线索排序；原始字段、来源和评分理由必须保留，方便复核，不能只保存模型结论。

### 3. 邮箱发现与验证

- 先从企业官网的 Contact、About、team、采购说明和公开展会资料中提取企业邮箱。
- 优先使用 `sales@`、`info@`、`procurement@` 等岗位邮箱；只有在公开职业信息明确且用途合适时，才记录个人工作邮箱。
- 对已知公司域名使用遵守条款的邮箱发现/验证服务；把“语法有效、域名有 MX、服务商判定可投递”与“本人同意接收营销”区分开。
- 不建议通过大量 SMTP 探测、社交平台批量抓取或购买来源不明的个人邮箱名单来“挖邮箱”。
- 建立抑制名单：退订、投诉、硬退信和删除请求一旦出现，后续流程自动阻断。

### 4. AI 邮件生成与发送闸门

为每封邮件提供结构化输入：公司事实、来源链接、匹配理由、目标岗位、价值主张和禁止编造的字段。模型只生成草稿，并强制输出引用的事实；程序检查：

- 收件人和公司是否匹配；
- 是否包含可验证的退订方式和发送主体；
- 是否出现未经证实的订单、合作关系、收入或个性化细节；
- 是否超过每日频率、重复发送或命中抑制名单。

发送前进入人工审核或小批量灰度队列。邮件服务使用正式的发信域名、SPF/DKIM/DMARC 和退信监控；不要用个人邮箱直接大批量发送。

### 5. 推荐的 MVP

先不要追求全自动群发，做一个可审计的半自动版本：

- 输入：一个 HS Code、一个目标国家、20 家企业。
- 自动完成：数据导入、域名标准化、官网摘要、产品匹配评分、邮箱候选和邮件草稿。
- 人工完成：确认企业和联系人、批准发送、处理回复和删除请求。
- 结果指标：有效企业匹配率、邮箱有效率、送达率、回复率、正向回复率、退订/投诉率和人工处理耗时。

建议的数据表至少包含 `companies`、`trade_records`、`contacts`、`evidence`、`campaigns`、`suppressions` 和 `audit_events`；API 密钥放在环境变量或密钥管理器中，不写入笔记、CSV 或代码仓库。
