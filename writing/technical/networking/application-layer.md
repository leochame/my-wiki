# DASH

DASH 全称 Dynamic Adaptive Streaming over HTTP，动态自适应流媒体传输。

## 要解决什么问题

传统 HTTP 流媒体只有一种画质。网速快的用户没问题，但网速慢的用户会卡顿。DASH 的做法是：同一个视频准备多个画质版本，客户端根据当前网速自动选择合适的版本来播放。

## 工作方式

1. 服务端把视频切成很多小块，每个块都编码成多个码率版本（高清、标清等）
2. 服务端生成一个 manifest 文件，记录每个块的每个版本对应的 URL
3. 客户端先下载 manifest 文件，解析后知道所有块的地址
4. 播放时，客户端一边下载一边播放，每次请求新块前都会评估当前网速和缓冲区状态，动态决定下一个块要请求哪个码率版本

所以 DASH 的核心决策权在客户端：请求哪个服务器、请求哪个画质，都由客户端根据实时网络状况决定。

## 单一数据中心的问题

如果所有视频都放在一个数据中心，直接向全球用户提供服务，会有三个问题：

- 距离远的用户，数据要经过很多中间网络节点，容易出现带宽不够导致卡顿
- 热门视频会在同一条链路上反复传输，浪费带宽
- 数据中心一旦故障，所有用户都受影响

这就是为什么需要 CDN。

# CDN

CDN（Content Distribution Network）即内容分发网络。核心思路：把内容提前复制到分布在全球各地的缓存服务器上，用户访问时，把请求导向离他最近、服务质量最好的节点。

## 服务器部署策略

CDN 节点怎么放，有两种思路：

- 深入接入网：在全球大量的接入 ISP（就是直接给用户提供网络的运营商）内部署小型服务器集群，离用户非常近
- 放在交换点：不进入 ISP 内部，而是在少数关键的互联网交换点（IXP，多个网络互联的地方）部署大型集群

节点部署好之后，CDN 会把内容复制到各个集群上。

## CDN 请求流程

以用户访问视频网站 NetCinema（使用第三方 CDN 服务商 KingCDN）为例：

1. 用户点击视频链接，浏览器对 `v.n.com` 发起 DNS 查询
2. 用户的本地 DNS（LDNS）把请求转发到 NetCinema 的权威 DNS 服务器。该服务器不直接返回 IP，而是返回一个 KingCDN 的域名，比如 `a.kingcdn.com`，相当于把请求交给了 CDN
3. LDNS 继续对 `a.kingcdn.com` 发起 DNS 查询，KingCDN 的 DNS 系统根据策略选出一个最合适的 CDN 节点，返回该节点的 IP 地址
4. LDNS 把这个 IP 地址返回给用户
5. 用户直接与该 CDN 节点建立 TCP 连接，发送 HTTP GET 请求获取视频。如果使用 DASH，服务器会先返回 manifest 文件

整个过程的关键在于：通过 DNS 重定向，用户的请求被透明地导向了 CDN 节点，用户本身感知不到。

## 集群选择策略

CDN 怎么决定把用户导向哪个节点？这就是集群选择策略。

最简单的方式是选地理位置最近的节点：通过 IP 地理位置数据库查出用户 LDNS 的位置，返回最近的集群。

但这个方法有明显缺陷：

- 地理距离近不等于网络距离近，中间可能绕了很多路由
- 有些用户配置了远端的 LDNS（比如用了公共 DNS），导致定位不准
- 完全不考虑实时网络状况，网速变化时无法调整

更好的做法是实时测量：CDN 让各个集群定期向全球的 LDNS 发送探测包，测量时延和丢包率，根据实际网络质量来选择节点。缺点是很多 LDNS 不响应探测请求，导致数据不完整。
