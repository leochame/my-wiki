## 1. 可靠数据传输

![[tcp-assets/tcp-rdt-reliable-data-transfer-overview.png]]
- 比特受损 - 差错检测，接收方反馈，重传
- 分组丢失 - 超时重传

我们已经假定完了比特受损，但是底层信道还会丢包。  
分组丢失，路由器具有 queue 队列，来了分组 push 进队列，队列如果满了就是丢弃。  
  
为了解决这个问题，rdt 加入了新的机制，超时重传机制。为了实现基于事件的重传机制，需要一个倒计数定时器，在一个给定的时间量过期后，可以中断发送方。因此，发送方要能做到：① 每发送一次分组，便启动一个定时器。② 响应定时器中断 ③ 终止定时器
![[tcp-assets/tcp-rdt-timeout-retransmission-state-machine.png]]

### 1.3 流水线可靠数据传输协议

Rdt 性能问题的核心在于它是一个停等协议。 链路容量比较大，一次发一个PDU 的不能够充分利用链路的传输能力 。所以我们提出了流水线，不以停等方式运行，允许发送方发送多个分组而无需等待确认。为了实现流水线技术，可靠数据传输协议做以下升级：  
- 增加序号范围，因为每个输送中的分组必须有一个唯一的序号，而且可能有多个输送中未确认的报文。  
- 协议的发送方、接收方两端缓存多个分组。发送方缓存已发送但是未确认的分组，接收方或许需要缓存已经正确确认的分组。  
- 序号范围和对缓冲的要求取决于数据传输协议如何处理丢失、损坏以及延时过大。解决这两个差错的两种方法：回退 N 步 和 选择重传。
![[tcp-assets/tcp-rdt-pipelined-gbn-sr-overview.png]]

###  1. 2 GBN

![[tcp-assets/tcp-gbn-sender-timeline.png]]

- send_base 定义为最早未确认分组的序号
- nextseqnum 定义为最小的未使用序号

那些已被发送但还未被确认的分组的许可序号范围可以被看成是一个在序号范围内长度为 N 的窗口。
随着协议的运行，该窗口在序号空间向前滑动。N 因此被称为窗口长度，GBN 也被称为滑动窗口协议。

#### GBN 中的发送方

GBN 发送方必须响应三种类型的事件：  
- 上层的调用。当上层调用 send()的时候，发送方首先检查发送窗口是否已满，即是否已有 N 个已发送但是未被确认的分组。  
	- 未满，产生分组将其发送，更新相应变量。  
	- 窗口已满，发送方数据返回上层，隐式提醒上层窗口已满，待会儿再试。  
	实际中，发送方会可能缓存这些数据，或使用同步机制允许上层仅在窗口不满的时候调用 send()。  
- 收到 ACK。在 GBN 协议中，对序号为 n 的分组确认采取累计确认方式，表明已经正确接收序号为 n 以及 n 以前的所有分组。
- 超时事件。使用定时器用于恢复数据或确认分组丢失。发送方使用一个定时器，它可被当作最早的已发送但未被确认的分组所使用的定时器。
![[tcp-assets/tcp-gbn-sender-fsm.png]]
![[tcp-assets/tcp-gbn-receiver-fsm.png]]
#### GNB 中的接收方
在 GBN 接收方中，序号为 n 的分组被正确接收，且按序（上一个交付给上层的数据是序号 n-1 的分组），则为分组 n 发送一个 ACK，并将数据交付上层。其他所有情况，丢弃分组。
这种方法看起来有些愚蠢。如果期望的 n，先到了 n+1，其实也可以将序号为 n+1 的分组缓存，交付完成 序号为 n 的分组后，再交付序号为 n+1 的分组。
优点就是不用缓存任何失序分组，接收方只需要维护 expectedseqnum 变量的更新即可。
![[tcp-assets/Pasted image 20260303213006.png]]


### 1.3 选择重传

在 GBN 中单个分组的差错引起 GBN 重传大量分组，许多分组没有重传的必要。选择重传协议通过让发送方仅重传那些他怀疑在接收方出错的分组而避免了不必要的重传。
SR 接收方将确认一个正确接收的分组而不管其是否按序。失序的分组被缓存直到所有丢失分组（即序号更小的分组）都被收到为止，这时才可以将一批分组按序交付给上层。

![[tcp-assets/tcp-sr-selective-repeat-overview.png]]

#### SR 发送者

1. **从上层收到数据。** 当从上层接收到数据，SR 发送方检查下一个可用于该分组的序号。如果序号位于发送方的窗口内，将数据打包发送；否则仍旧像 GBN (Go-Back-N) 中一样，要么缓存数据，要么返回给上层以便以后传输。
2. **超时。** 定时器被用来防止丢失分组，但是与 GBN 不同的是，**每个分组都必须拥有自己的逻辑定时器**。
3. **收到 ACK。** 如果收到 ACK，倘若该分组在窗口内，则 SR 发送方将那个被确认的分组标记为已被接收。如果该分组的序号等于 `send_base`，则窗口基序号向前移动到具有最小序号的未确认分组处。窗口移动，有序号落在窗口内，发送这些分组。

#### SR 接收者

1. 序号在 [rcv_base,rcv_base+N−1] 内的分组被正确接收。返回一个 ACK，如果该分组没收到过则缓存。 如果分组序号等于接收窗口的基序号，则该分组以及以前缓存的序号连续的分组交付给上层。然后，接收窗口向前移动分组的编号向上交付这些分组。
2. 序号在 [rcv_base−N,rcv_base−1] 内的分组被正确接收。此时产生一个 ACK，即使该分组是接受方以前已确认的分组。    
3. 其他情况。忽略。

## 2. TCP — 面向连接的传输

TCP 被称为是面向连接的，在一个应用进程可以向另一个应用进程发送数据之前，他们必须互相发送某些预备报文段，确保数据传输的参数。
TCP 连接提供全双工服务：一台主机的进程 A 与另一主机的进程 B 存在一条 TCP 连接，应用数据可从进程 B 流向 A，也可从 A 流向 B。TCP 连接也是点对点的，即单个发送方与单个接收方之间的连接。

### 2.1 TCP 报文结构

![[tcp-assets/tcp-segment-header-format.png]]
- sequence number 序号字段：是指在整个字节流中的偏移量。
	- ![[tcp-assets/tcp-sequence-number-stream-example.png]]
- acknowledgement number 确认号字段：如果该值为 n，代表 n 以前（不包括 n）的序号接收完成，期望 n 及 n 以后的序号的传输。
- receive window 接收窗口字段：提供流量控制  
- options 选项字段 : 该字段用于发送方与接收方协商最大报文段长度（MSS）时，或在高速网络环境下用作窗口调节因子使用。  
- 标志字段

> 什么是 TCP 的捎带机制，TCP 的 ACK 失序怎么办？

主机 A 在收到第二个报文段之前收到第三个报文段，也就说第三个报文段失序到达，在实践中我们采用接收方保留失序的字节，并等待缺少的字节以填补间隔。发送 ACK 的时候确认号还是第二个报文段的序号。  
对客户到服务器的数据的确认被装在在一承载服务器到客户数据的报文中；这种确认被称为是捎带（piggybacked）在服务器到客户的数据段报文中。

### 2.2 往返估计与 TimeOut

TCP 也是采用超时重传机制来处理报文段丢失问题。超时间隔长度必须大于该连接的往返时间（RTT)，一个报文段发出到它被确认的时间

报文段的样本 RTT（SampleRTT）就是从某报文段被发出（交给 IP）到收到对该报文段的确认之间的时间量。
大多数 TCP 的实现仅在某个时刻做一次 SampleRTT 测量，而不是测量每一个发送的报文段。也就是说，在任意时刻，仅为一个已发送但目前尚未被确认的报文段估计 SampleRTT，从而产生一个接近每个 RTT 的新的 SampleRTT 的值。  
值得注意的是，TCP 绝不为重传的报文段计算 SampleRTT，仅为传输一次的报文段测量 SampleRTT。

由于路由器的拥塞和端系统负载的变化，这些报文段的 SampleRTT 值会随之波动。因此，为了估计一个典型的 RTT，自然要采取某种对 SampleRTT 取平均的方法。TCP 维持一个 SampleRTT 的均值（EstimatedRTT)。一旦获得一个 SampleRTT，TCP 就会更新 EstimateRTT :  
$EstimateRTT=(1-\alpha)×EstimateRTT + \alpha×SampleRTT$
> 这里的 α 的推荐值为 0.125。  

除此之外我们定义了 RTT 偏差 DevRTT, 用于估算 SampleRTT 的偏离程度:  
$DevRTT=(1−β)×DevRTT+β×∣SampleRTT−EstimatedRTT$
> 这里的 β 推荐值为 0.25。

这时候设置超时间隔为：
$TimeoutInterval=EstimatedRTT + 4×DevRTT$
推荐初始的 TimeoutInterval 值为 1s。同时，当出现超时后，TimeoutInterval 值将加倍，以免确认即将被确认的后继报文段过早出现超时。


### 2.3 可靠数据传输

TCP 在 IP 服务之上创建了一种可靠的数据传输服务。TCP 的可靠数据传输服务确保一个进程从其接收缓存中读出的数据流是无损坏、无间隙、非冗余和按序的数据流。
主要依赖于 RTT 的基本原理：【差错检测】、【重传】、【累计确认】、【定时器】以及【用于序号和确认号的字段】。

#### 2.3.1 重传定时器

之前的可靠数据传输中，我们假定为每一次发送但是未确认的报文段与一个定时器关联。但是这样多个定时器的管理需要很大的开销。那该怎么办呢？
我们使用单一的重传定时器。 TCP 中即使有多个已发送但还未被确认的报文段，定时器管理过程仅使用单一的定时器。

![[tcp-assets/tcp-single-retransmission-timer.png]]

#### 2.3.2 Timeout 间隔加倍

大多数 TCP 实现中做了一些修改。首先就是定时器时限过期后超时间隔长度。每当超时事件发生，TCP 重传具有最小序号的还未被确认的报文段。每次重传超时间隔都会设置为原来的两倍。然而每当定时器在另两个事件（收到上层应用的数据，收到 ACK）发生时，TimeoutInterval 由最近的 EstimatedRTT 值与 DevRTT 值推算得到。

#### 2.3.3 快速充传

如果 TCP 收到三个冗余 ACK，将认为报文段丢失，执行快速重传。
![[tcp-assets/tcp-fast-retransmit-example.png]]
超时出发重传存在的问题之一是超时时间过长。发送方通常可以通过冗余 ACK 检测丢包情况。  
冗余 ACK 就是再次确认某报文段的 ACK，而发送方先前已经确认过了。也就说如果有四个 确认序号一样的 ACK 传来，只有第一个是正常的，后面三个都是冗余 ACK。  
当TCP 接收到一个其序号大于期望序号的报文段，它检测到数据流中的间隔。这个间隔可能是报文段丢失也有可能是重排序。因为 TCP 不使用否定确认，只会返回已接受到的最后一个按序字节数据进行重复确认（即产生一个冗余 ACK）。

![[tcp-assets/tcp-duplicate-acks-example.png]]


#### 2.3.4 错误恢复机制

TCP 的差错恢复机制其实更像是 GBN 和 SR 的混合体。  
TCP 发送方仅需要维持已发送过但未被确认的字节的最小序号（SendBase）和下一个要发送的字节的序号（NextSeqNum）。这时 TCP 像 GBN。  
但是 TCP 实现会将正确接收但失序的报文段缓存。当一组报文段 1~N 到达，进一个序号为 n 的报文段丢失。TCP 至多会重传一个报文段就是 n。这就是 TCP 的选择确认（selective acknowledge，sack），即允许 TCP 接收方有选择的确认失序报文段，而不是累积的确认最后一个正确接收的有序报文段。

### 2.4 流量控制

TCP 连接的每一侧主机都为该连接设置了缓存，存在接收缓存溢出的可能。  

TCP 提供了流量控制服务来消除发送方使得接受方缓存溢出的可能性。因此 TCP 的流量控制服务是一个速度匹配服务，即发送方的发送速率和接收方应用程序的读取速率相匹配。  TCP 通过让发送方维护一个称为接收窗口的变量来提供流量控制。接收窗口用于给发送方一个指示，该接收方还有多少可用缓存空间。

值得注意的是，要区分开拥塞控制，它是为了解决 IP 网络拥塞的问题。

![[tcp-assets/tcp-flow-control-receive-window.png]]

主机 B 通过把当前的 rwnd 值放入它发送给主机 A 的报文段接收窗口，通知主机 A 它在该连接的缓存还有多少空间。

![[tcp-assets/Pasted image 20260304103213.png]]
这里有一个小小的注意点，假设当主机 B 接收窗口 rwnd=0 时，再假设主机 B 不再有数据给主机 A。而当主机 B 中的缓存清理完毕，TCP 中主机 B 仅当它又数据或者确认要发送的时候才会发给主机 A 。  
所以，主机 B 清空缓存，也不会向主机 A 发送带有 rwnd 新值的报文，主机 A 不会知道主机 B 的接收缓存已有新空间。  
为了解决这个问题，TCP 规范中要求：当主机 B 的接收窗口为 0，主机 A 继续发送只有一个字节数据的报文段。这个报文段将会被接收方确认。最终缓存开始清空，确认报文的 rwnd 不为 0。
![[tcp-assets/tcp-zero-window-probe.png]]

### 2.4 TCP 的连接管理

#### 2.4.1 三次握手的流程

连接的本质是要和对方通信，准备好资源，尤其是 recvbuffer 大小要告诉对方。

客户端中的 TCP 与服务器的 TCP 连接的建立：  
1. 客户端 TCP 首先向服务端的 TCP 发送一个SYN 报文段。    
	- 在报文段的首部中  SYN 比特 标志位被设置为 1  
	- 客户端会随机地选择一个初始序号（client_isn）
2. 一旦 SYN 报文段到达服务器，服务器会为 该 TCP 连接分配 TCP 缓存和变量，并向该客户端发送允许连接的报文段。报文段的首部包含三个信息：  
	- SYN 比特设为 1。  
	- TCP 报文段首部的确认号为 client_isn+1。  
	- 服务器选择自己的初始序号（server_isn)，将其放在 TCP 报文段首部的序号字段中。  
	该报文段被称为 SYNACK 报文段（SYNACK segment）。  
3. 收到 SYNACK 报文段后，客户也要给该连接分配缓存和变量。  
	同时客户端主机则向服务器发送另外一个报文段，这是一个报文段对服务器允许连接的报文段进行 ACK。因为连接已经建立，所以 SYN 比特设为 0，从现在开始也就是从第三阶段开始，可以在报文段负载中携带客户到服务器的数据。

但是注意： 在完成第三步之前，分配这些 TCP 缓存和变量存在受到泛洪攻击的可能性 
![[tcp-assets/tcp-three-way-handshake.png]]

#### 2.4.2 为什么不采用两次握手

半连接问题。超时重新进行的连接发生在连接关闭后，就会发生客户主机的半连接问题，客户端认为连接存在，但是主机并没有建立连接。会存在无效浪费资源的问题
![[tcp-assets/tcp-two-way-handshake-half-open-problem.png]]

重复数据传输问题。服务器造成重复传输数据造成一个数据传输不一致问题。
![[tcp-assets/tcp-two-way-handshake-duplicate-data-problem.png]]

#### 2.4.3  关闭进程
参与 TCP 连接的两个进程都能关闭进程。假设客户端打算关闭连接。  
1. 客户端应用进程发出关闭连接命令，发送一个首部中的标志位即 FIN 比特设置为 1。  
2. 服务器接收到后，就向发送方回送一个确认报文。  
3. 然后服务器再发送一个他自己的终止报文段，其 FIN 比特设为 1 。  
4. 客户端对这个服务器的终止报文发送一个确认报文。
![[tcp-assets/tcp-connection-teardown-four-way-fin.png]]

#### 2.4.4 SYN 泛洪攻击

服务器为了响应一个收到的 SYN，分配并初始化连接变量和缓存。然后服务器发送一个 SYNACK 进行响应，并等待来自客户的 ACK 报文段。如果某客户不发送 ACK 来完成该三次握手的第三步，最终服务器将终止该半连接并回收资源。  
这种 TCP 连接管理协议为经典的 DOS 攻击即 SYN 泛洪攻击提供条件，这种攻击中，攻击者发送大量 TCP SYN 报文段，而不完成第三次握手。随着 SYN 报文纷至沓来，服务器，不断为这些半连接分配资源 。

幸运的是，SYN cookie 可以解决这个问题。其工作方式：  
1. 服务器收到 SYN 报文段，该服务器不会为该报文段生成半开连接，而是先生成一个初始 TCP 序列号。
	该序列号是 SYN 报文段的源和目的 IP地址与端口号以及仅有该服务器知道的秘密数的一个复杂函数。这种精心制作的初始序列号被称为 "cookie"。
	服务器则发送具有这种初始序列号的 SYNACK 分组。服务器并不记忆该 cookie 或任何对应于 SYN 的其他状态信息。  
2. 如果客户是合法的，则它将返回一个 ACK 报文段。
	服务器收到该 ACK，需要验证 ACK 是否与之前发送的 SYN 是否对应。服务器没有维护有关 SYN 报文段的记忆，所以它是借助于 cookie 实现的对于一个合法的 ACK，在确认字段中的值等于在 SYNACK 字段（此时为 cookie）中的值加 1。
	服务器则将使用在 SYNACK 报文段中的源和目的地 IP 地址与端口号以及秘密数运行相同的散列函数。该函数的结果加 1 与客户的 SYNACK 中的确认 （cookie）值相同，服务器认定该 ACK 合法。服务器才会生成一个具有套接字的全开的连接

### 2.5 补充


我们考虑当一台主机接收到一个 TCP 报文段，其端口号或源IP 地址与该主机上进行中的套接字不匹配的情况。一台主机接收到了具有 80 端口的一个 TCP SYN 分组，但该主机在端口 80 不接受连接。则该主机向源发送一个特殊的重置报文段。该 TCP 报文段将 RST 标志位置为 1。

nmap不仅能”侦察“打开的 TCP 端口，也可以侦察 UDP 端口、防火墙及配置、应用程序版本和操作系统。  
  
为探索目标主机上的一个特定 TCP 端口，比如 80，nmap 端口扫描工具将对那台主机的目的端口 6789 发送一个特殊的 TCP SYN 报文段，将会有三种输出：  
1. 源主机从目标主机接收到一个 TCP SYNACK 报文段。这意味着 TCP 80 端口运行，被一个目标主机的应用程序使用，nmap 返回”打开“。  
2. 源主机从目标主机接收到一个 TCP RST 报文段。这意味着该 SYN 报文段到达了目标主机，但目标主机没有运行一个使用 TCP 端口 80 的运行程序。  
3. 源主机什么也没收到。这表明 SYN 报文段可能被中间防火墙阻挡。

## 3. 拥塞控制

1. 发送方一般不知道路由器缓存区的大小。如果发生拥塞，这时候可能会造成报文丢失，那将触发重传机制。那么在网络通道中会大量充斥着重发的报文。这就是网络拥塞的代价之一，发送发必须执行重传以补偿缓存溢出而丢弃的分组。发送也有可能提前重传超时报文，造成信道中存在两个相同报文。
2. 当一个分组沿一条路径被丢弃，每个上游路由器用于转发该分组而使用的传输容量就被浪费了。

### 3.1  TCP 拥塞控制
”经典“的 TCP 采用端到端的方法解决拥塞控制，因为 IP 对端系统不提供明确的的涉及网络拥塞的反馈。

#### 3.1.1 经典 TCP 拥塞控制

TCP 发送方通过感知它到目的地是否发生拥塞来调整其发送速率。同时我们也会面临以下三个问题：  
1. 如何限制向其连接发送流量。  
2. 如何感知从它到目的地之间路径是否存在拥塞。  
3. 感知到拥塞时采用什么算法改变发送速率。

运行发送方的 TCP 拥塞控制机制跟踪一个额外的变量，即拥塞窗口（cwnd）。拥塞窗口对一个 TCP 发送方能向网络中发送流量的速率进行限制。

$LastByteSent-LastByteAcked<=min [cwnd, rwnd]$

如果发生丢包事件，发送方就认为发生拥塞。TCP 发送方通过调节 cwnd 值以控制发送速率的机制。

**TCP 以下方为指导性原则回答这些问题**：
1. 一个丢失的报文意味拥塞，丢失报文时降低 TCP 发送方速率。 
2. 先前未确认报文段到达，增加发送方速率。  
3. 带宽探测。
---

#### 3.1.2 TCP 拥塞算法

该算法主要包括三部分：  
1. 慢启动
2. 拥塞避免
3. 快速恢复

##### 慢启动

- 初始状态： 连接建立时，$cwnd$ 初始值通常被设置为 1MSS ( 最大报文段长度）。  
- 增长方式： 指数级增长。发送方每收到一个新的确认 (ACK)，就将$cwnd$ 增加 1MSS

一个 RTT（往返时间）内，$cwnd$ 值会翻倍（因为每发送一个 MSS 都会收到一个 ACK）。

----

那么何时结束慢启动呢？慢启动的目的是快速探测网络带宽，但不能持续太久，以免引起拥塞。它主要有三种结束方式：
1. 达到阈值 (最理想情况),慢启动结束，当  $cwnd$  达到或超过 $ssthresh$ 的值时。  
	- TCP 转入拥塞避免 (Congestion Avoidance) 阶段。
2. 发生超时, 发送的报文段超时未收到 ACK（被认为是严重丢包，网络可能已严重拥塞），重新进入慢启动状态。
	- 更新阈值 $ssthresh=cwnd/2​$  将当前窗口的一半作为新的阈值）。  
	- 重置窗口 $cwnd=1MSS$
	- 进入慢启动： 重新回到慢启动阶段。  
3. 收到 3 个冗余 ACK，进入快速恢复 (个别丢包)， 发送方连续收到 3 个对同一报文段的冗余 ACK（表明网络中仍有数据流动，是个别丢包）。  
	- 执行快速重传：立即重传被认为丢失的报文段。  
	- 进入快速恢复 (Fast Recovery) 阶段。

##### 拥塞避免

进入条件： 从慢启动切换而来，此时$cwnd$﻿ 的值等于 $ssthresh$
增长方式： 线性增长（加性增，Additive Increase）。  
速率：每当收到一个 ACK 时，cwnd 增加 1/cwnd。
目标： 谨慎地、线性地探测更大的可用带宽，避免再次引起拥塞。

---

拥塞避免主要因检测到丢包事件而结束，其遇到以下两种情况与慢启动阶段处理相同：  
1. 发生超时 (严重拥塞)  
	- 更新阈值 $ssthresh=2cwnd​$  将当前窗口的一半作为新的阈值）。  
	- 重置窗口 $cwnd=1MSS$
	- 进入慢启动： 重新回到慢启动阶段。  
2. 收到 3 个冗余 ACK (个别丢包)：  
	- 执行快速重传：立即重传被认为丢失的报文段。  
	- 进入快速恢复 (Fast Recovery) 阶段。

##### 快速恢复

这两种机制是为应对“个别丢包”设计的，目的是在不经历超时和慢启动重置的情况下，尽快恢复传输。  

进入快速恢复的条件，当发送方收到 3 个冗余 ACK 时，进入快速恢复
- 快速重传： 发送方立即重传被冗余 ACK 指示的丢失报文段。  
- 更新阈值：$ssthresh=cwnd/2​$  
- 更新窗口 (窗口膨胀)：$cwnd=ssthresh+3×MSS$
	解释：$cwnd$ 减半是对拥塞的承认。额外的 3×MSS 是因为这 3 个冗余 ACK 证明有 3 个数据包离开了网络（它们的 ACK 已经“在路上”）。这个膨胀的$cwnd$ 是一个临时状态。  

恢复过程中（窗口膨胀期），如果继续收到冗余 ACK： 
- 每再收到一个冗余 ACK，说明又有 1 个报文段离开了网络。 $cwnd$ 临时增加 1MSS  ( $cwnd=cwnd+1MSS$)。  
- 作用： 维持“膨胀”的 $cwnd$ 允许发送方在等待重传报文段 ACK 的同时，继续发送新的数据包，保持数据流不中断，充分利用网络管道。  

退出快速恢复的条件  ： 
1. 收到一个确认了新数据的 ACK（通常是确认了被快速重传的那个丢包，以及其后的数据）。  窗口重置：$cwnd$ 的值被重置为第一步中计算的 $ssthresh$ 。( $cwnd=ssthresh$)。  
	解释： 临时膨胀的 $cwnd$ 任务完成，必须收缩。重置到 $ssthresh$ 是一个保守、安全的起点。  
2. 同时 算法直接转入拥塞避免 (Congestion Avoidance) 阶段，不会回到慢启动。


#### 3.1.2 TCP 拥塞算法补充

回顾上阶段，忽略到开始时的慢启动，TCP 的拥塞控制是：每个 RTT 内 cwnd 线性增加 1MSS，出现 3 个冗余 ACK 事件时 cwnd 减半。因此，TCP 拥塞控制也被称为加性增，乘性减（Additive-Increase，Multiplicative-Decrease，AIMD）拥塞控制方式。

##### TCP Reno 和 TCP Tahoe

快速恢复是 TCP 推荐而非必须，对比以下两个版本：

TCP 的早期版本 TCP Tahoe 不管发生超时还是 3 个冗余 ACK，都无条件地将 rwnd 减至 1 个 MSS，并进入慢启动阶段。
TCP 较新版本 TCP Reno 则综合了快速恢复。  

两者算法大致一致，对于丢包事件判断都是以重传超时（retransmission timeout，RTO）和重复确认为条件，但是对于重复确认的处理，两者有所不同：  
- Tahoe：如果收到三次重复确认——即第四次收到相同确认号的分段确认；
	1. 慢启动阈值改为当前拥塞窗口的一半
	2. 拥塞窗口降为1个MSS
	3. 重新进入慢启动阶段。  
- Reno：如果收到三次重复确认，Reno算法则进入快速重传：
	1. 拥塞窗口减半来跳过慢启动阶段
	2. 慢启动阈值设为当前新的拥塞窗口值
	3. 进入快速恢复

对于RTO，两个算法都是将拥塞窗口降为1个MSS，然后进入慢启动阶段。

##### TCP CUBIC

TCP CUBIC的核心思想：改变之前降低发送速率太过于谨慎，如果出现丢包的链路处阻塞的状态变化不大，让发送速率迅速接近丢包前发送速率，并且在那时才谨慎的探测带宽。

TCP CUBIC 和 TCP Reno 略有不同。CUBIC 保留了 仅当收到 ACK 时增加拥塞窗口，同时保持慢启动和快速恢复。
TCP CUBIC 仅仅改变拥塞避免阶段：
1. Asumme
	- $W_{max}$ 为最后检测到丢包时 TCP 阻塞控制窗口的长度。  
	- $K$ 是假设无丢包情况下，再次到达 $W_{max}$ 的未来时间节点。几个可调整 CUBIC 参数决定 K，也就说决定协议拥塞窗口多快到达 Wmax  
2. TCP CUBIC 拥塞窗口以 $f（x）$形式增加，而 $f（x$）是当前事件 $t$和 $K$ 之间的立方距离函数。这意味着离 $K$ 越近，拥塞窗口长度增加越谨慎，并且到达  $W_{max}$ 才开始谨慎探测带宽。  
3. 当 $t$ 大于 $K$ 时 : 
- 立方规则意味着当  $t$ 仍然接近 $K$ 时，CUBIC 的拥塞窗口增加很小(引起丢包的链路的拥塞级别变化不大)
	- 但是当 $t$ 超过 $K$ 的程度过大时，CUBIC 的拥塞窗口增加很快。这使得如果引起损失的链路的拥塞级别发生明显变化，CUBIC 可以更快地找到新的工作点。

### 3.2 BBR 

传统的拥塞控制算法（如 CUBIC）极其“鲁莽”，它们的工作逻辑是：“只要没丢包，我就拼命加速；一旦丢包，我就断崖式减速。”

现代网络环境下会产生两个严重问题：

- 缓冲区膨胀 (Bufferbloat)： 现代路由器的缓存很大。CUBIC 会把这些缓存填满，导致数据包在路由器排队，造成极高的延迟（RTT 飙升），但由于还没丢包，CUBIC 觉得一切正常。

> 	内部超时时间 （ RTO = SRTT + 4 × RTTVAR ）， 不是一个固定值，而是根据 RTT 动态调整的。只要数据包在缓存里排队后最终被转发了，发送端就能收到确认。只要能收到确认，计时器就会重置。所以，尽管用户感觉到延时增加，但从协议的角度看，连接是“健康”的，并不会触发超时重传。

- 高误判率：在现代长距离链路（如跨海光缆）或移动网络中，丢包往往是因为链路噪声，而不是真正的拥塞。CUBIC 一看到丢包就减速，导致吞吐量极低。


BBR 彻底抛弃了“丢包即拥塞”的旧观念。BBR 实时监测两个物理量：

1. 最大带宽 (BtlBw)： 测量当前这段网络路径一秒钟最多能处理多少数据。
    
2. 最小延时 (RTprop)： 测量数据包在网络中不排队、纯跑完物理距离所需的最短时间


BBR 为了能在不丢包的情况下找到网络的最优传输点，会在以下四个状态中不停切换：

1. Startup（启动）： 连接刚开始时，发包速度指数级增长。直到发现带宽不再增加（即使再加速，收到的确认包速度也没变快），就记录下这个最大带宽，切换状态。

2. Drain（排空）： 因为启动阶段发得太快，网络节点里肯定堆积了没处理完的数据。这个阶段会主动大幅降低发包速度，直到把之前堆积的数据全部消耗掉，让延迟降下来。

3. ProbeBW（探测带宽）： 这是最常驻的状态。它以 8 个数据包为一个周期：先提速（1.25 倍）看带宽上限有没有提高；再降速（0.75 倍）排掉刚才多发的包；最后 6 个周期按 1 倍速平稳发送。

4. ProbeRTT（探测时延）： 每隔 10 秒左右，强制把发包量降到极低（通常只发 4 个包左右），持续 200 毫秒。这样是为了清空网络上所有的排队，测出数据包纯物理传输的最短时间。

但是，v1 版本对“丢包”不敏感和抢占带宽太厉害

- 当 BBR 流量和传统的 CUBIC 流量在同一个窄路竞争时，BBR 往往会抢走大部分带宽，导致使用老算法的用户速度变得极慢。

- 在极度拥塞的极端环境下，BBRv1 有时会因为对丢包太不敏感而持续高速发包，导致整个网络段彻底瘫痪

BBRv2 做出了以下改进：

- 引入丢包阈值： 设定一个具体的丢包率上限（比如 2%）。如果测量发现丢包率超过这个值，BBRv2 就会直接降低发送速度，不再像 v1 那样只盯着带宽看。

- 降低探测性攻击： 在 ProbeBW 阶段，BBRv2 调低了提速的比例，并且会参考丢包反馈来调整窗口，避免把使用 CUBIC 等老算法的流量挤到完全没速度。

### 3.3 QUIC 的拥塞控制

1. 解决了重传歧义

	- TCP 使用相同的序列号（Sequence Number）进行重传。当收到 ACK 时，接收端分不清这是原始包的确认还是重传包的确认，导致 RTT 计算偏差。

	- 每一个数据包都有一个**单调递增的 Packet Number**。即使是重传的内容，也会使用新的 Packet Number。这样发送方能精确区分每一个 ACK 对应的是哪个物理包，从而获得极准的 RTT 采样。

2. 引入 ACK Delay 和更丰富的确认信息

	- QUIC 的 ACK 帧中包含了从接收到包到发送确认之间的延迟时间（ACK Delay），发送方在计算 RTT 时会扣除这部分时间，避免了因接收方延迟确认导致的拥塞窗口误缩。

3. 连接迁移的出现，复用旧的连接

	- TCP 使用“五元组”标识连接，当你在 WiFi 和 4G 切换时，IP 变化会导致 TCP 连接断开。QUIC 使用 **Connection ID** 标识连接，只要 ID 不变，即使底层 IP 变了，拥塞控制状态也可以延续，无需重新“慢启动”。‘

> 既然每个包的编号都在变，接收方怎么知道 Packet 12 里的内容其实就是 Packet 10 丢掉的那些数据呢？
> 
> 这就靠包里的 **Frame（帧）** 信息：
> 
	Stream ID：标识这段数据属于哪个流（比如图片 A 还是脚本 B）。
	Offset（偏移量）：标识这段数据在整个流中的具体位置（比如是图片 A 的第 1024 到 2048 字节）。
