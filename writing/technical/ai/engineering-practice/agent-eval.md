
任务具有明确输入和成功标准的单个测试。
每次尝试完成任务都称为一次**试验** 。由于模型输出在不同运行中会有所变化，因此我们会进行多次试验以获得更一致的结果。

**核心评估指标**

-  二元测试：只有对或错，基于二元测试的话，可以演化出评分机制。
- pass k
	- pass@k： 在 k 次尝试中至少获得一次正确解的概率。适用于只需一次成功即可的任务（如代码修复）。
	- pass^k： 在 k 次尝试中全部成功的概率。衡量一致性，对面向客户的可靠性至关重要。

**评估者：**
	- 代码可以做成 脚本检测,单元测试，适合有很明确的结果的任务，可以使用代码衡量的。比如：竞赛，然后严格对应的。
	- 人类专家来进行评估，在这个领域，模型没有人更懂这个场景
	- 专门的评估模型：
	  代码测试（如单元测试）只能进行死板的字符串匹配或数值验证。评估模型能够理解语义，即使智能体输出的句式与参考答案不同，只要意思正确，评估模型依然能判定为通过。
	 相比于雇佣人类专家逐条阅读和打分，调用评估模型（如具有强推理能力的大模型）可以在几分钟内完成海量数据的自动化测试，大幅降低资金和时间成本。

评估的任务：
	- **能力或“质量”评估**会问：“这个智能体擅长做什么？”评估应该从较低的通过率开始，针对智能体难以完成的任务，给团队设置一个挑战。
	- **回归评估**旨在询问“代理是否仍然能够处理之前的所有任务？”，其通过率应接近 100%。回归评估可以防止系统退步，因为分数下降表明某些环节出现问题，需要改进。团队在进行能力评估时，同时运行回归评估至关重要，以确保变更不会在其他地方引发问题。
	代理程序启动并优化后，通过率高的能力评估可以“升级”为回归测试套件，持续运行以检测任何偏差。以前衡量“我们能否完成这项任务？”的任务，现在可以衡量“我们是否仍然能够可靠地完成这项任务？”

必须包含完整的上下文，包括 `System Prompt`（智能体的角色定义）、`User Input`（用户问题）、`Agent Output`（待评估的回答），以及可选的 `Reference Answer`（参考答案/Ground Truth）。
在进行 Pair-wise 对比时，模型容易偏好放在前面（或后面）的选项。**设计方案：** 在后台自动运行两次评估，第一次是 A vs B，第二次交换顺序为 B vs A。只有两次结果一致时才采纳，不一致则判定为平局或交由人类仲裁

### 自动化评测（来自langchain 社区的方法分享）


自动优化真正难的，是设计评价信号（Evaluation Signal）

这是一个经典的启发式搜索和优化算法。逻辑很简单：你站在山腰，随机向四周迈出一步：
- 如果效果变好，你就站在这里继续找下一步；
- 如果效果变差，就退回来。
在 LLM 领域，这意味着系统会自动微调 Prompt，如果测试得分更高就保留，否则丢弃，不断迭代直到找到“局部最优解”

让另一个大模型（或自身）作为“优化器”，对当前的 Prompt 提出修改建议。用修改后的 Prompt 跑一遍数据集，根据预设的“评价信号”打分。如果分数比原来高，就采纳新的 Prompt（成功向山顶走了一步）；如果分数低，就退回原版。重复上述步骤。

“爬山算法”或者大模型自我反思（Self-Refine）的代码逻辑其实并不复杂，很容易实现自动化。自动化优化的核心前提是——**机器得知道什么是“好”，什么是“坏”**。如果你设计的评价标准（评价信号）是有偏差的，那么自动化算法就会朝着错误的方向狂奔。

优化循环通常会发现并验证以下类型的变更：
- **提示词与指令更新**：修复工具输出格式理解错误或过于激进的工具调用。
- **工具套件优化**：更新工具描述，添加如何链式使用工具的示例，或消除相似工具间的歧义。

将用户纠正 Agent 的轨迹转化为高质量的评估案例，形成“使用越多 -> 轨迹越多 -> 评估越强 -> Harness 越好”的飞轮。

一个严谨的自动化评估体系由以下核心要素组成：

|组件名称|定义与作用|
|---|---|
|**任务 (Task/Problem)**|单个测试用例，包含定义的输入和成功准则。|
|**尝试 (Trial)**|对单个任务的一次运行。由于模型具有随机性，通常需要多次尝试以获得一致性结果。|
|**评分器 (Grader)**|衡量性能的逻辑。分为基于代码（确定性）、基于模型（LLM-as-judge）和人工评审。|
|**轨迹/追踪 (Trace/Transcript)**|试验的完整记录，包括推理、工具调用、中间结果和环境交互。|
|**结果 (Outcome)**|环境的最终状态（例如：数据库中是否真的生成了订单，而非仅仅是智能体声称已下单）。|
|**评估架构 (Harness)**|运行评估的基础设施，提供工具、记录步骤、聚合结果。|
|**评估套件 (Suite)**|旨在衡量特定能力或行为的一组任务集合。|


### 评估方法

针对软件工程任务，直接利用 GitHub 上的真实 Issue，要求 Agent 提供端到端的代码修改并运行测试。

由人类开发者或标注人员对 Agent 的行为轨迹进行审查和评分。通常用于涉及高风险操作、主观性强或现有自动化指标无法准确衡量真实体验的场景。

常见的有：



**核心能力评估**

1. 工具调用与 API 执行 (Tool Calling)：Agent 是否正确选择了工具？是否遗漏了必需的参数？是否捏造（Hallucinate）了不存在的参数名或超出了允许的数值类型？
2. 规划与多步推理：Agent 将复杂目标拆解为子目标的能力。常用的指标是“进度率 (Progress Rate)”，即衡量 Agent 在多步任务中已经完成了多少比例的子任务，哪怕最终任务失败，也能评估其推进能力。
3. 记忆机制：Agent 提取和利用短期上下文以及长期存储信息的能力。测试 Agent 在经历了多轮对话或长时间运行后，是否还能准确调用之前的关键状态或用户设定的规则。
4. 反思与纠错：当环境返回报错信息（如 API 调用失败、语法错误）时，Agent 能够根据错误日志自动修正自身行为并重新尝试的成功率。
5. 长上下文的能力。
