# 1 演进
## 1.1 多线程->多进程->线程池

服务器要同时服务很多客户端，最直接就是一连接一线程（或进程）。

但线程创建/销毁有开销，也占资源，连接一多就撑不住。

所以会用「线程池」：少量线程处理大量连接。

但是，新问题是：单连接单线程时，一般是「read -> 业务处理 -> send」。如果没数据可读，线程会卡在阻塞的 `read` 上，只影响自己。

线程池里，一个线程不能一直堵在某个连接上，就把 socket 设成非阻塞，不停 `read` 去轮询谁有数据。

---

问题在于，线程不知道哪个连接现在能读，只能反复 `read` 试探。

这样虽然不阻塞，但很耗 CPU，连接越多越低效。

更好的做法是，真有数据再去读。

这就用 I/O 多路复用：一个系统调用监听多个连接，让一个线程同时等很多 I/O 事件。

## 1.2 反应堆模型的由来

我们熟悉的 `select` / `poll` / `epoll` 是内核提供的 I/O 多路复用系统调用，线程可以一次从内核拿到多个事件。

后来大家在这个能力上做了封装，让上层不用关心底层网络 API，只关注业务逻辑，这就是 **Reactor 模式**。

Reactor 的核心思想是：**I/O 多路复用统一监听事件，收到事件后，根据类型分发给对应的处理逻辑**。

Reactor 模式里，主要有两块：

+ Reactor：负责监听和分发事件（连接、读写等）；
+ 处理资源池：负责实际处理，例如 `read` -> 业务逻辑 -> `send`。

根据 Reactor 数量和处理资源池规模不同，可以组合出几种常见方案：

+ 单 Reactor 单进程 / 线程；
+ 单 Reactor 多进程 / 线程；
+ 多 Reactor 多进程 / 线程。

具体用进程还是线程，和语言、平台实现有关，比如 Java 常用线程，C 里进程和线程都有人用。

接下来分别看这几种经典的 Reactor 方案。

# 2 Reactor
## 2.1 单 Reactor 单进程 / 线程
单 Reactor 单进程 / 线程的实现里，一个进程（或线程）里有三个核心组件：**Reactor、Acceptor、Handler**。

+ Reactor：通过 `select`（I/O 多路复用）监听事件并分发；
+ Acceptor：负责接收新连接；
+ Handler：负责处理读写和业务逻辑。

流程大致是：

+ Reactor 通过 `select` 监听事件，收到后根据类型 `dispatch` 给 Acceptor 或 Handler；
+ 如果是新连接事件，由 Acceptor 调用 `accept` 建立连接，并创建对应的 Handler；
+ 如果是普通读写事件，由对应连接的 Handler 通过 `read` -> 业务处理 -> `send` 完成。

这个方案实现简单，所有逻辑都在一个进程 / 线程里，不用考虑进程间通信或多线程并发问题。

缺点也很明显：

+ 只能用到一个核，**多核 CPU 利用率不高**；
+ 业务处理在 Handler 里执行时，**无法同时处理其他连接事件，耗时业务会拉高整体延迟**。

所以，单 Reactor 单进程 / 线程更适合业务处理很快、主要瓶颈不在 CPU 的场景。

## 2.2 单 Reactor 多线程 / 多进程
为了解决单 Reactor 单进程 / 线程无法利用多核、业务处理易阻塞的问题，可以把业务处理丢给子线程或子进程，形成**单 Reactor 多线程 / 多进程**。

单 Reactor 多线程的大致流程是：

+ 前三步和单 Reactor 单线程一样：Reactor 监听事件并分发，Acceptor 接收连接并创建 Handler，普通事件交给对应 Handler；
+ 不同的是，Handler 只负责收发数据：`read` 读到数据后，**把业务处理交给子线程里的 Processor**；
+ 子线程里的 Processor 处理完业务，再把结果交回主线程中的 Handler，由 Handler 通过 `send` 写回 client。

这样做的优点是：**可以利用多核 CPU 提升吞吐**。但也会带来多线程共享数据、加锁、协调等并发问题，例如子线程把结果交回主线程时的共享状态管理。

单 Reactor 多进程在设计上类似，但要处理复杂的进程间通信和连接路由，实际用得比较少，多数场景直接用多线程方案。

此外，「单 Reactor」还有一个共性问题：**所有事件监听和分发都集中在一个 Reactor 上，在高并发场景下容易成为性能瓶颈**。

## 2.3 多 Reactor 多进程 / 线程
为了解决单 Reactor 的集中瓶颈，可以把接收连接和处理连接拆开，形成 **多 Reactor 多进程 / 线程**：

+ 主线程里的 MainReactor 只通过 `select` 监听「新连接事件」，收到后由 Acceptor 调用 `accept` 建立连接，并把连接分配给某个子线程；
+ 子线程里的 SubReactor 接管这个连接，把它加入自己的 `select` 进行监听，并创建 Handler 处理后续的读写事件；
+ 之后的事件处理流程和前面一样，Handler 通过 `read` -> 业务处理 -> `send` 完成。

这个方案的好处是：主线程只管接新连接，子线程专心处理业务，职责清晰，又能利用多核，提高整体吞吐。

多 Reactor 多线程在很多框架里都在用，多 Reactor 多进程在 Nginx 等项目中也有应用，常见做法是主进程负责初始化，具体的 `accept` 和事件处理交给子进程里的 Reactor。

# 3 Proactor
## 3.1 阻塞、非阻塞、同步、异步 I/O
前面说过，Reactor 用的是**非阻塞同步**模式，**Proactor 用的是异步模式**。先把这几个 I/O 概念捋一下。

阻塞 I/O：调用 `read` 后，线程一直等，直到内核把数据准备好、并从内核拷贝到用户缓冲区，整个过程都在等。

非阻塞 I/O：调用 `read` 时如果数据没准备好会立刻返回，应用程序可以继续干别的，不断轮询内核，等数据准备好，再由内核把数据拷贝到用户缓冲区，这一次 `read` 才真正拿到数据。

这里要注意：**最后一次拷贝数据到用户态的过程还是同步的，需要等**。所以，不管是阻塞还是非阻塞 I/O，本质上 `read` / `send` 调用里真正拷贝数据这一步都是同步的。


**异步 I/O** ：**数据准备和拷贝这两步都不用应用线程等待**。应用发起 `aio_read` 之后就直接返回，内核在后台完成数据准备和拷贝，完成后再通知应用，应用不需要自己主动去发起拷贝。Proactor 就是基于这种异步 I/O 的网络模型。

## 3.2 Proactor 和 Reactor 的不同
有了上面的铺垫，再看两者区别就很简单了：

+ **Reactor：非阻塞同步模式，感知的是「就绪可读写事件」**；
+ **Proactor：异步模式，感知的是「已完成的读写事件」**。

可以这么理解：Reactor 里，内核只是告诉你「事件到了」，实际的读写由应用自己做；Proactor 里，内核负责把 I/O 操作做完，再把结果交给应用处理。

两者本质上都是「事件分发」模式，不同点在于：**Reactor 基于「待完成」的 I/O 事件，Proactor 基于「已完成」的 I/O 事件**。

在实现层面，Linux 下标准的 `aio` 系列更多是用户态模拟，只支持本地文件异步，socket 不完善，所以高性能网络库大多用 Reactor。Windows 下有操作系统级别的 `IOCP`，是真正支持 socket 异步 I/O 的接口，更适合实现 Proactor 模式。

# 4 总结
常见的 Reactor 实现有三种：

1. 单 Reactor 单进程 / 线程：实现最简单，但只能用一个核，业务处理不能太慢，更适合轻量快速的场景，比如早期 Redis。
2. 单 Reactor 多线程：用了多线程，但只有一个 Reactor 负责所有连接的事件监听和分发，在高并发下容易成为瓶颈。
3. 多 Reactor 多进程 / 线程：把接收新连接和处理读写拆开，主 Reactor 负责接新连接，从 Reactor 负责具体读写，Netty、Memcache、Nginx 等都采用了这一思路的变种。

Reactor 是非阻塞同步模式：事件就绪后，内核通知应用，由应用自己去 `read` / `write`。Proactor 是异步模式：内核把 I/O 做完，再把结果交给应用。

两者本质上都是事件分发，区别在于：Reactor 基于「待完成」的 I/O 事件，Proactor 基于「已完成」的 I/O 事件。
