
## 1. IO 模型到底在解决什么

IO 操作的本质是用户空间缓冲区和内核空间缓冲区的相互拷贝。

1. 等待网络数据到达 NIC（读取准备）/等待 NIC 可写（写入准备）-> 读/写到内核缓冲区

2. 从内核缓冲区复制数据到用户空间（读）/从用户空间复制数据到内核缓冲区（写）

在 Linux 中，IO 对象是文件（因为一切都是文件）。对于正常文件，IO 会涉及 DMA、磁盘和 CPU。对于套接字文件，sendfile 技术也会被包括在内。

## 2. 同步 vs 异步， 阻塞 VS 非阻塞

这四个概念经常被混在一起说，最好拆开来看：

- **阻塞 / 非阻塞**：关注的是**一次系统调用期间，线程要不要“傻等”**  
  - 阻塞：`recvfrom()` 没有数据时，当前线程会睡眠，直到数据准备好并拷贝完成才返回。  
  - 非阻塞：`recvfrom()` 没有数据时**立即返回**错误码（如 `EAGAIN` / `EWOULDBLOCK`），线程不会被挂起，可以去做别的事，但通常需要自己“再来问一次”。

- **同步 / 异步**：关注的是**整个 IO 请求生命周期里，谁来“主动推进”和“等待完成”**  
  - 同步：从发起请求到数据真正就位，整个过程都需要调用方自己参与，比如：发起系统调用 → 轮询 fd 是否就绪 → 再次调用读接口完成拷贝。  
  - 异步：调用方只负责**提交请求**，后续的等待、数据准备、拷贝都由内核或 IO 子系统负责，最后只收一个“完成通知”（回调 / 事件 / 信号）。


## 3. Linux 下读一次数据：从系统调用到数据到达（抽象视角）

不管使用哪种 IO 模型，从“程序想读数据”到“数据真正写进用户空间缓冲区”，大致都会经过下面这些步骤：

1. **应用发起系统调用**  
   比如调用 `recvfrom()` / `read()` / `recv()`，传入 fd、用户态缓冲区地址和长度。

2. **内核检查自己这边有没有数据**  
   - 如果数据已经在 socket buffer / page cache 里，就可以直接进入拷贝阶段。  
   - 如果还没有（例如网络包还没收完），内核需要等待网卡和协议栈把数据收到并放进缓冲区。

3. **等待数据进入内核缓冲区（第一段等待）**  
   - 阻塞 IO：当前线程被挂起，放入等待队列，直到数据准备好。  
   - 非阻塞 IO：系统调用立即返回错误码（如 `EAGAIN`），什么时候再来读由应用自己决定。  
   - IO 多路复用：线程阻塞在 `select/poll/epoll_wait` 上，由这些系统调用统一等待哪些 fd 变成可读。  
   - 异步 IO：应用线程不参与这一步，由内核或 IO 子系统在后台等待。

4. **内核把数据拷贝到用户空间缓冲区（第二段等待）**  
   - 在同步 IO（包括阻塞 / 非阻塞、多路复用）里，这一步在当前线程里完成，拷贝结束后系统调用才返回。  
   - 在真正的异步 IO（例如 `io_uring` 的某些模式）里，这一步可能由内核或专门的 worker 完成，应用只在最后收到一次“拷贝完成”的通知。

5. **系统调用返回，应用拿到结果**  
   通常会返回本次实际读取的字节数或错误码，应用再根据协议决定是否继续读取、以及如何解析这些数据。

从这个角度看，不同 IO 模型的主要差异集中在第 3 步和第 4 步：  
是谁在等待数据、是谁执行拷贝，是在当前线程里做，还是交给内核或后台线程去做。

## 4. 五种经典 IO 模型

理解它们的关键在于区分“数据准备阶段”（等待数据到达内核缓冲区）和“数据拷贝阶段”（将数据从内核空间拷贝到用户空间）中，进程的状态是什么。

![[linux-io-assets/io-models-five-types-overview.png]]
### 4.1 阻塞 IO（blocking IO）

所谓阻塞IO就是当 Application 发起读取数据申请时，在内核数据没有准备好之前，Application 会一直处于等待数据状态，直到内核把数据准备好了交给 Application 才结束。

> 在操作系统层面即：当进程调用 `recvfrom` 等系统调用时，如果数据还没准备好，进程就会被**挂起（阻塞）**，直到数据就绪并从内核拷贝到用户空间后，进程才被唤醒。


### 4.2 非阻塞 IO（non-blocking IO）

非阻塞IO就是当 Application 发起读取数据申请时，如果内核数据没有准备好会即刻告诉 Application ，不会让B在这里等待。

> 操作系统理解为：如果应用程序调用 recvfrom 读取数据时缓冲区中没有数据，非阻塞 IO 将返回 EWOULDBLOCK 错误，不会让应用程序等待。当没有数据时立即返回错误标志，这意味着如果应用程序想要读取数据，它需要不断地调用 recvfrom 请求（我认为这是内部的无限循环），直到读取到所需的数据。

### 4.3 IO 多路复用（select/poll/epoll）

如果在并发的环境下，可能会N个 Application 发送消息，这种情况下我们的应用就必须创建多个线程去读取数据，每个线程都会自己调用recvfrom 去读取数据。

![[linux-io-assets/io-multiplexing-multi-thread-problem.png]]

IO 多路复用解决了这个问题，由极少数线程同时监听多个文件描述符（FD）的状态，仅在数据就绪时才触发后续处理，从而以极小的资源开销实现了对海量并发请求的高效管理。

> 进程调用 `select`、`poll` 或 `epoll`，这些系统调用可以**同时监控多个文件描述符**。
> 
> 我们以 select 为例，select函数监控的fd中只要有任何一个数据状态准备就绪了，select函数就会返回可读状态，这时询问线程再去通知处理数据的线程，对应线程此时再发起recvfrom请求去读取数据。

![[linux-io-assets/io-multiplexing-select-epoll-flow.png]]

### 4.4 信号驱动 IO（SIGIO）
多路 IO 模型解决了线程可以监视多个文件描述符的问题，但选择使用 polling 来监视多个文件描述符，不断对文件描述符的可读状态进行 polling，以判断数据是否可读，无脑的 polling 有点暴力，因为大多数情况下 polling 无效。所以信号驱动的 IO 模型是衍生的。

当 sigaction 被调用时，
1. 建立一个 SIGIO 信号连接
2. 当内核数据准备就绪时，线程会通过 SIGIO 信号通知应用程序数据的可读状态
3. 当线程接收到可读状态的信号时，它会发起一个 recvfrom 请求，请求内核读取数据

因为根据信号驱动的 IO 模型，应用程序线程可以向监视器发出信号，然后这样，应用程序线程也可以同时监视多个文件描述符。
 ![[linux-io-assets/io-signal-driven-model.png]]

### 4.5 异步 IO（AIO）
前 4 种模型在“数据从内核拷贝到用户空间”这一步都是阻塞的。
而异步 IO（如 Linux 的 `AIO` 或 `io_uring`）则彻底不同：程序简单地向内核发送读取请求，告诉内核它想要读取数据，并立即返回；内核接收请求并建立信号连接，当数据准备就绪时，内核会主动将数据从内核复制到用户空间。**内核完成数据准备和拷贝的全过程**后，再通知进程。
