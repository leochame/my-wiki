JIT 的核心难点在于 “如何让一块内存既能写代码，又能跑代码”。这就是 `mmap` 发挥作用的地方。
1. JIT 引擎调用 `mmap` 向操作系统申请一块内存。此时，它会请求 **可写** 权限。
2. JIT 编译器将高级语言代码转换成十六进制的机器指令（比如 x86 的 `0x55` 代表 `push rbp`），并把这些字节直接写入刚才申请的 `mmap` 内存区域。
3. 为了安全（遵循 **W^X** 原则，即“可写不可执行，可执行不可写”），一旦机器码写完，JIT 引擎会调用 `mprotect` 改变这块内存的权限，**修改为：** `PROT_READ | PROT_EXEC`（去掉 `WRITE` 权限，增加 `EXECUTE` 权限
4. JIT 引擎通过一个函数指针，指向这块 `mmap` 内存的起始地址，然后直接调用它。


	`mprotect` 是一个系统调用，用于修改已经分配的内存页面的访问权限。


GDB 能够观察和控制另一个进程，核心依赖于内核提供的 `ptrace` 系统调用。当 GDB 调试一个程序时，它是“父进程（Tracer）”，被调试的程序是“子进程（Tracee）”。

> **`ptrace`** 是允许一个进程（Tracer）观察和控制另一个进程（Tracee）的执行状态，并能读写其内存和寄存器。

**新进程启动 (`run`)：**
1. GDB 调用 `fork()` 创建子进程。
 2. 子进程在执行 `execve()` 加载 `a.out` 之前，先调用 `ptrace(PTRACE_TRACEME, ...)`。
3. 这一步会在内核中将该进程标记为 `PT_PTRACED` 状态。当子进程执行 `execve` 时，内核会向其发送 `SIGTRAP` 信号，使其在执行第一条指令前挂起，将控制权交给父进程（GDB）。
**附加到现有进程 (`attach`)：**
    1. GDB 调用 `ptrace(PTRACE_ATTACH, pid, ...)`。
    2. 内核检查权限后，向目标进程发送 `SIGSTOP` 信号使其停止，并建立 Tracer（GDB）与 Tracee（目标进程）的从属关系。

一旦建立了 `ptrace` 关系，目标进程接收到的所有信号（除了无法捕捉的 `SIGKILL`）都会被内核拦截，并通知 GDB。GDB 通过 `waitpid()` 等待信号，分析原因后决定是让目标进程继续运行（`PTRACE_CONT`）还是单步执行（`PTRACE_SINGLESTEP`）。


目标进程的内存布局的建立由内核加载器（通常是 `ld-linux.so`）和 GDB 对调试符号的解析共同完成：
- `a.out` 解析，GDB 读取 `a.out`（ELF 格式）的文件头、程序头表（Program Header Table）和符号表（.symtab / .debug_info）。通过这些数据，GDB 获知代码段（`.text`）、数据段（`.data`）以及调试信息中的虚拟地址偏移。
- 内存映射 (`mmap`)： 
	1. 当目标进程启动时，内核加载器使用 `mmap(2)` 系统调用将 `a.out` 的各个段映射到虚拟地址空间。
	2. 代码段通常被映射为 `PROT_READ | PROT_EXEC`（可读、可执行，不可写）。数据段被映射为 `PROT_READ | PROT_WRITE`。
    
-  如果系统启用了 ASLR，GDB 会通过内核接口获取动态装载的实际基地址，并结合 ELF 文件的相对偏移，计算出指令在内存中的精确位置。


Breakpoint & Code Modificatio
- **指令替换：** 当你在 GDB 中输入 `break *address` 时，GDB 会利用 `ptrace(PTRACE_PEEKTEXT, address, ...)` 读取该地址处的原始机器码（例如 X86 架构下的 `0x55`）。
- **植入 0xCC：** GDB 使用 `ptrace(PTRACE_POKETEXT, address, 0xCC, ...)` 将该地址的首字节替换为 `0xCC`。在 X86 指令集中，`0xCC` 对应 `INT 3` 指令。
- **触发异常：** 当 CPU 执行到该地址时，解析到 `INT 3`，触发一个“断点陷阱”异常。
- **内核响应：** 内核捕获异常后，向进程发送 `SIGTRAP` 信号。由于 `ptrace` 关系，该信号被 GDB 拦截。




## 进程通信

管道 ：
	匿名管道是在内核中开辟的一段**内存缓冲区**。它具有固定的读端和写端。
	命名管道是在文件系统中创建一个特殊的**文件节点**，不相关的进程可以通过打开这个特定的文件路径来进行通信

消息队列：
	消息队列是由内核维护的一个**消息链表**。

共享内存 ：
	不同进程的虚拟地址经过页表映射后，指向同一块物理内存区域。进程可以直接读写这块内存，不需要在内核态和用户态之间进行数据拷贝。

信号量：
	常与共享内存配合使用，确保同一时间只有一个进程在修改内存。
	
信号：
	内核在特定事件发生时（如硬件异常、进程非法操作、键盘输入中断），向目标进程发送一个整数信号。接收进程可以预先注册信号处理函数（Handler）来响应不同的信号。

套接字：
	通过 IP 地址和端口号在不同主机间交换数据。


# 线程切换

在 Linux 和类似操作系统中，线程与进程在调度层面统一作为任务（Task）处理，核心区别仅在于是否共享虚拟内存地址空间。

**1. 触发阶段： 什么情况下才会触发切换**

- 主动放弃： 线程执行了阻塞型的系统调用（例如等待网络数据、读取磁盘、申请锁失败或主动休眠），此时线程状态变更为阻塞，并直接调用调度程序让出 CPU。
    
- 被动抢占： 硬件定时器产生时钟中断，内核在处理中断时发现当前线程分配的时间配额已耗尽，或者有更高优先级的线程处于就绪状态。此时内核会标记当前线程需要被重新调度。

**2. 状态保存，从用户态到内核态**

无论是系统调用还是硬件中断，都会导致 CPU 从用户态切换至内核态。

- 在此瞬间，硬件和操作系统的底层入口代码会将当前线程在用户态的执行状态（主要是程序计数器、用户栈指针以及通用寄存器）直接压入该线程专属的**内核栈**中保存。
- 此时，当前线程仍在运行，只是运行的地点从用户空间转移到了内核空间。

**3. 核心切换阶段：执行调度与移交控制权**

确认需要切换后，当前线程会在内核态开始执行核心的切换逻辑：

1. 当前线程执行调度程序代码。调度程序会先锁定系统状态以防多核冲突，然后从就绪队列中挑选出下一个目标线程。
2. 切换虚拟内存地址空间
	-  如果目标线程与当前线程属于不同进程，系统会修改 CPU 的页表基址寄存器，指向新进程的内存映射表。这会导致 CPU 内部的地址缓存（TLB）失效，是跨进程切换性能损耗的主要原因。
	- 如果两者是同一进程下的不同线程，由于共享内存，系统会直接跳过此步骤
3. 切换底层寄存器
	- 当前线程将自己内核态的关键寄存器（特别是内核栈指针和内核返回地址）保存到自己的内存结构 ( `task_struct` ) 中。
	- 紧接着，系统将目标线程 `task_struct` 中保存的寄存器数据加载到 CPU 物理寄存器中。

 当 CPU 的栈顶指针被修改为目标线程的内核栈指针时，CPU 的执行流就已经在物理层面上完成了移交。

**4. 恢复执行阶段：返回用户态**

目标线程沿着它上一次在内核中被挂起时的代码位置继续往下执行（例如，完成之前未结束的中断处理或系统调用）。

目标线程的内核代码执行完毕准备退出时，会从它自己的内核栈中，弹出在第 2 阶段保存的用户态程序计数器和栈指针。

CPU 权限级别降低，指令指针跳回目标线程在用户态的代码位置，目标线程继续执行业务逻辑。整个切换过程闭环。
