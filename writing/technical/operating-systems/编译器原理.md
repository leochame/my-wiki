

编译优化的顺序并非绝对的线性执行。**局部优化**（在一个基本块内）和**全局优化**（跨越多个基本块，涉及流分析）通常是**交替进行**或迭代进行的。
窥孔优化是一种“极其局部”的优化技术，它通过一个滑动窗口（窥孔）观察几条相邻的指令，并尝试用更快的指令序列替换它们。
常量折叠，如将 `3 + 5` 直接计算为 `8`）可以发生在多个阶段
循环优化在中间代码阶段实施效果通常优于目标代码阶段



## 编译器设计的几个阶段

1. 词法分析。 这是最基础的一步。编译器会扫描你写的源代码字符流，把它们拆分成一个个有意义的单元，我们管这些单元叫 **Token（记号）**。
	- **输入**：`int a = 10;`
	- **处理**：识别出 `int` 是关键字，`a` 是变量名，`=` 是赋值符号，`10` 是常数，`;` 是结束符
2. 语法分析。会根据编程语言的规则检查你的代码结构是否合法。它会把这些 Token 组装成一个树状结构，AST 树。如果你的代码少写了一个括号或者分号，编译器在这一步就会报错，因为它无法构建出一棵符合逻辑的树。
3. 语义分析。主要进行**类型检查**。比如，你是否尝试把一个字符串加到一个整数上？或者你调用的变量是否根本没有定义？
4. 中间代码生成，在确认代码没问题后，编译器不会直接跳到机器码，而是先生成一种**中间代码 (IR)**。这种设计是为了让编译器更容易跨平台。一套中间代码可以通过不同的后端适配到 x86、ARM 等不同架构上。
5. 代码优化。这是提升程序性能的关键步骤。编译器会分析中间代码，寻找可以改进的地方。比如删除永远不会执行的代码段（死代码），或者把循环里重复计算的部分提到循环外面。
6. 目标代码生成。编译器把优化后的中间代码转换成特定 CPU 能够直接执行的指令，为变量分配寄存器，把操作转换成具体的机器指令（如 `MOV`, `ADD` 等）。


### 代码优化

局部优化 (Local Optimization) 与 全局优化 (Global Optimization)，
- **局部优化**：只针对一个“基本块”（Basic Block，即一段没有跳转进出的顺序代码）进行分析。它的视野很窄，只看当前的几行指令。
- **全局优化**：视野更广，它会跨越多个基本块，分析整个函数内的逻辑流。
两者并不是先做完一个再做另一个，而是经常**交替、迭代**进行。比如全局优化简化了逻辑后，可能又会出现新的局部优化机会。

窥孔优化。编译器像通过一个很小的孔（滑动窗口）看代码，一次只看相邻的两三条指令。最常用于**目标代码生成阶段**。，比如把刚存进内存的值立刻又读出来的废操作（STORE 紧跟 LOAD）删掉，或者用更高效的硬件指令替换。

常量折叠，简单来说就是“提前算账”。如果代码里写了 `3 + 5`，编译器在编译时就直接把它换成 `8`，这样程序运行时就不用再做加法了。它非常灵活，可以发生在语义分析、中间代码优化，甚至是最后的目标代码阶段。

循环优化，最适合在**中间代码 (IR) 阶段**做。循环是程序运行最耗时的地方。在 IR 阶段，代码的逻辑结构（如循环边界、变量变化规律）非常清晰，比已经变成乱序指令的机器码更容易分析。常见的操作包括把不随循环变化的计算移到循环外面（代码外提）。

公共子表达式删除，如果代码中多次计算同一个复杂结果（比如 `a * b + c` 出现了好几次），且中间变量没变，编译器会只算一次，然后把结果存起来反复用。

复写传播，如果你写了 `x = y; z = x + 1;`，编译器会直接理解成 `z = y + 1;`。这能消除不必要的变量中间转手，为后续其他优化（比如发现 `x` 没用了）创造条件。

强度削弱，用更轻量的运算代替重运算。比如在循环里，把 `i * 4` 这种乘法变成 `prev_val + 4` 这种加法，因为 CPU 做加法通常比乘法快得多。

函数内联，如果一个函数很小且被频繁调用，编译器会直接把函数体内容“拷贝”到调用的地方。省去了函数调用时压栈、跳转、返回的开销，这在高性能 C++ 开发中非常关键。


### 底层的硬件概念

- **RISC（精简指令集）：** 它的指令非常短，而且长度是固定的。每一条指令只干一件非常简单的事。因为指令整齐划一，CPU 的硬件电路可以设计得非常简单、高效，非常适合排成“流水线”。
- **CISC（复杂指令集）：** 它的指令长度不固定，有的很短，有的很长。一条指令可能包含了好几个动作。虽然对程序员来说一条指令能干更多事，但对 CPU 硬件来说，拆解这些复杂的指令非常费劲，很难整齐地排进流水线。

CPU 执行一条指令通常分为几个步骤：**取指**（从内存拿指令）、**译码**（看指令要干嘛）、**执行**（计算结果）、**访存**（去内存读写数据）、**写回**（把结果存入寄存器）。

**流水线结构**就是让 CPU 不用等一条指令完全走完这 5 个步骤才开始下一条。当第一条指令在做“译码”时，第二条指令就可以开始“取指”了。这样 CPU 的各个部件每一时刻都在工作，不闲着。


----

数据冒险（Data Hazard）与 RAW

流水线虽然快，但会带来逻辑上的冲突，这就是“冒险（Hazard）”。
指令 A 计算 1+1=2，要把结果存到寄存器 `R1`。紧接着指令 B 要读取 `R1` 的值去加 5。在流水线里，指令 A 还没运行到最后的“写回”步骤，`R1` 里的值还是旧的。此时指令 B 已经运行到“执行”阶段要去读 `R1` 了。如果它直接读，读到的就是错的数据。


**暂停（Stall）：** 强行让指令 B 在原地等几个时钟周期，直到指令 A 把结果写进 `R1`。这在时序图上看起来像出现了一个空档，所以叫“流水线气泡”。

**旁路/前推（Forwarding）：** 这是一个硬件小技巧。既然指令 A 已经在“执行”阶段算出结果是 2 了，虽然还没存进寄存器，但硬件直接拉一根线，把这个 2 直接传给指令 B 的计算单元。这样指令 B 就不用等了。

 **乱序执行：** CPU 发现指令 B 在等指令 A，于是先去后面找找有没有跟 A、B 都没关系的指令 C，先把 C 给做了。

---
结构冒险（Structural Hazard）

如果 CPU 只有一个内存访问接口。某一时刻，指令 A 正在“访存”阶段从内存读数据，而指令 E 正在“取指”阶段也要从内存读指令。内存接口只有一个，没法同时给两个人用。

只要硬件资源（如内存端口、计算器）不够，流水线就必须停下来一个

流水线预测

在流水线结构中，CPU 每一刻都在尝试取下一条指令。但是，当你写了一个 `if (a > b)` 时，这个“比较”动作是在流水线的执行阶段（Execute）才算出结果的。


`if (data[i] > 100)` 的结果很有规律（比如前面全是 False，后面全是 True），CPU 的预测准确率接近 100%。


### 分支预测

流水线效率损失，是站在 **CPU 整体利用率**的角度看的

CPU 执行一条指令，硬件上是分工明确的。为了方便说明，我们看这三个关键部件：
1. 取指单元（Fetch）： 负责从内存里拿指令。它必须知道一个目标地址，才能去拿指令。
2. 译码单元（Decode）： 负责分析指令。
3. 执行单元（Execute）： 负责计算。`if` 的比较结果（是真还是假）是在这一步才算出来的。

流水线的工作目标是：取指单元每一时刻都在拿新指令。流水线为了高效率，必须在当前指令还没做完时，就去拿下一条指令。

遇到 `if` 语句时，CPU 需要等该指令运行到中后期（执行阶段）才能算出结果。
在算出结果前，CPU 不知道下一条指令的内存地址在哪。如果原地等待，取指单元就会闲置，产生“流水线气泡”，导致硬件利用率减半。

CPU 内部有一个记录表，会记下这行代码以前是“跳”还是“不跳”。不需要等计算结果，取指单元根据历史记录直接“盲猜”一个路径，把后面的指令先塞进流水线跑起来。
如果 `if` 执行完发现猜错了，CPU 必须立即停止工作。流水线里所有已经取进来、跑了一半的“错误指令”全部被扔掉（清空流水线）。CPU 回到发生判断的地方，重新去正确的地址取指令。这种“白干活”加上“重新填满”的过程非常耗时。


### 循环优化

1. 代码外提，如果在循环内部有一个表达式，它的值在每次循环时都不变（即不依赖于循环变量），那么编译器就会把它搬到循环外面去执行。
```
for (int i = 0; i < 100; i++) {
    a[i] = x + y; // x + y 每次结果都一样
}

优化后

int temp = x + y; 
for (int i = 0; i < 100; i++) { 
	a[i] = temp; 
}

```

2. 强度削弱，用执行速度更快的算术运算替换较慢的运算。最典型的是在循环中用加法替换乘法。

```
for (int i = 0; i < 100; i++) { 
	a[i] = i * 4; // 每次都要做乘法 
}

优化后

int acc = 0;
for (int i = 0; i < 100; i += 2) { 
	a[i] = acc;
	acc += 4; // 换成加法，CPU 处理速度更快
}

```
3. 循环展开 ，通过增加循环体的内容来减少迭代次数，从而减少循环条件判断的次数。
```
for (int i = 0; i < 100; i++) {
    process(i);
}

after optimize

for (int i = 0; i < 100; i += 2) {
    process(i);
    process(i + 1);
}
```
编译器之所以不总是激进地展开成 100 次，是因为一个物理法则：**指令缓存（Instruction Cache, I-Cache）是有限的。**

如果你把每一个循环都展开 100次，你的可执行文件会从几 MB 变成几百 MB。如果是一个小循环，整段代码可以完全装进 I-Cache。CPU 只需要在这一小块高速内存里反复循环，速度极快。如果你展开了 1000 次，代码长度超过了 I-Cache 的容量。CPU 每执行几行代码就要去 L2 甚至内存里拉取下一段指令。这种访存延迟会彻底抵消掉“省去循环判断”带来的那点性能提升。

4. 循环交换。在嵌套循环中，改变循环的内外顺序，使内存访问更符合“空间局部性”（通常是按行访问）。在 C/C++ 中，多维数组是行优先存储。如果按列遍历，会产生大量的 Cache Miss。
